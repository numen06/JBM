# 大屏资源版本与空间

入口：JBM 管理工作台 → 大屏管理 → 版本与空间。建筑平台继续使用 JBM 大屏模块，不维护第二套发布或清理流程。

## 保留规则

- 默认保留 **当前版本 + 最近 2 个历史版本**；每个大屏可以选择总计 1～5 个版本。仅留当前版时不可回滚。
- 当前版保留运行目录和 ZIP；历史版仅保留 ZIP 和少量元数据，不重复解压。历史位于 `views` 同级的 `.views-history`，不在公开静态资源目录中。两者的父目录均须持久化（镜像默认 `/app/data`）。
- 上传包、重新加载和回滚共用发布流程；成功保存元数据后才淘汰超额历史，同一内容不重复归档。发布失败会恢复原运行目录和 ZIP，不淘汰历史。
- 回滚是把历史包重新发布为新版本，保留当前名称、租户、项目绑定和保留设置。被替换的当前包按同一规则进入历史。
- 降低保留数量立即清理超额历史。当前 ZIP 缺失时暂不清理，损坏时拒绝清理，优先保留恢复机会。
- “立即清理”会校验当前 ZIP，归并该大屏已识别的 `.zip.bak-日期/版本`，淘汰超额 ZIP 与旧展开目录；其他大屏正在引用的路径不会删除。不认识的文件不会猜测删除。
- 成功发布、手工清理与服务启动时删除超过 24 小时的已识别上传临时文件。恢复失败留下的救援工作目录不自动删除，应人工核查。
- 删除大屏会清除运行资源、当前 ZIP 和受管历史，共享运行资源仍受保护；本功能不清理 Docker 镜像、业务数据库或开发机中的发布文件。

## 接口与权限

以下 POST 接口沿用大屏管理权限（平台管理员或本租户管理员），所有操作按租户校验大屏归属：

| 路径（服务内） | 请求 | 用途 |
| --- | --- | --- |
| `/bigscreenView/storage` | `id` | 当前/历史/旧备份占用与可回滚版本 |
| `/bigscreenView/retention` | `id`, `keepVersions` | 总保留数（整数 1～5） |
| `/bigscreenView/prune` | `id`, `includeLegacy: true` | 归并旧备份、按策略清理，返回释放字节数 |
| `/bigscreenView/rollback` | `id`, `revisionId` | 校验历史 ZIP 后重新发布 |

保留设置存入已有 `extendData.resourceRetention.keepVersions`，不需要建表或项目专用种子数据。未配置的大屏自动使用默认规则。

当前镜像单进程写入，用进程锁串行化资源变更；同一个资源卷不能同时运行多个写入进程。未来需要多副本写入时，再替换为共享锁和事务恢复日志。

验证：在 `jbm-python-cluster` 运行 `python -m pytest bigscreen/tests -q`，覆盖数量限制、回滚、失败恢复、重复发布、旧备份归并、临时文件、共享路径保护和租户权限。
