# JBM、IoT、建筑平台版本与环境发布 SOP

适用环境：公网云平台、党校等独立部署环境，以及开发/预生产环境。三个仓库独立构建、独立递增版本；同一环境通过发布清单记录三者实际运行的组合。本文沿用各仓库现有的 `py-*` 和云端 `cloud-*` 镜像命名，不另起一套版本号。

## 1. 版本的四个身份

每次发布必须同时记录：

1. **源码**：仓库名、完整 Git commit 与对应 Git 发布标签。打版本前必须提交本次代码；未提交工作区不能作为正式版本来源。
2. **构建**：App2Docker 任务 ID、所用配置文件/profile、各服务镜像的唯一标签、架构（AMD64/ARM64）。
3. **运行**：各 Swarm 服务实际使用的 `仓库@sha256:<OCI 索引摘要>`，而不是构建时的可变标签。
4. **数据**：数据库迁移 revision、备份位置及校验值。JBM、IoT 和建筑平台分别记录；不把应用版本等同于数据库版本。

镜像标签只用于找到构建结果。标签一经推送不得重用或覆盖，跨环境晋级时复用同一镜像摘要，不重新构建同名标签。三个平台可以处于不同版本，环境清单必须准确列出其组合。

## 2. 沿用现有命名

| 平台 | 正式镜像标签 | 云端专项快照的现有命名 | 发布配置入口 |
| --- | --- | --- | --- |
| JBM | `py-7.3.<递增版本>` | 按对应发布配置中的既有标签 | JBM7 `.app2docker.yaml`、`scripts/release-python-images.ps1` |
| IoT | `py-2.1.<日期>.<序号>` | `cloud-<YYYYMMDD>.<序号>` | iot-platform-jbm `.app2docker.yaml`、`.app2docker-cloud.yaml` |
| 建筑 | `py-2.1.<日期>.<序号>` | 对应 cloud profile 中既有的 `cloud-*` / `cloud-building-*` | smart-building-platform-py `.app2docker.yaml`、对应 `.app2docker-cloud*.yaml` |

以发布时实际使用的 profile 为准，先查现有最大版本，再在同一系列递增。不同仓库的日期序号不要求相同；不得为了视觉统一改变已有镜像名或旧标签。新标签发布前应查询仓库，确认不存在。

## 3. 发布前冻结与检查

1. 确定目标环境、服务清单和回退窗口；列出三个平台当前运行的镜像摘要、服务副本数、数据库 revision、设备在线数和关键队列/任务状态。
2. 核对本地 `git status`，将本次要发布的代码、迁移、资源和测试提交并推送；排除凭据、`.env`、数据库、缓存、测试输出及本地密钥。发布标签必须指向包含全部本次改动的提交。仍有其他本地改动时，用干净的 Git checkout/工作树按该提交构建。
3. 按平台跑相关自动测试、前端类型检查和生产构建；对有迁移的版本，在生产库副本上演练迁移。保存结果。
4. 备份本次会触及的数据存储及服务规格，验证备份可读取且校验值匹配。仅新增表/索引也要备份对应数据库；未更改 TDengine 时不要为了应用发布重置其数据。
5. 优先使用 App2Docker 的 Git 源构建。先推送代码与同名 Git 标签，并验证构建工作树 `HEAD`、远端发布分支和标签都指向同一个提交；工作区若有其他未提交内容，使用干净的发布工作树及已设置 upstream 的发布分支。显式指定 Git 标签、profile 和镜像新标签。例如 IoT 云端：

   ```powershell
   git rev-parse HEAD
   git rev-list -n 1 cloud-YYYYMMDD.N
   app2docker build --source git --tag-name cloud-YYYYMMDD.N --profile cloud --tag cloud-YYYYMMDD.N --push --detach --json
   app2docker task status <task-id>
   ```

   立即检查任务解析出的 `tag`、`config_source`、`source_mode`、Git ref 和全部服务标签。Git 源构建必须指向刚推送的提交；CLI 所在目录要有本次配置。发现旧标签、错误 profile、错误提交或错误服务范围，推送前停止任务并核查仓库摘要；停止响应后仍须复查任务最终状态。仅在 Git 源构建不可用时，才从该提交的干净 checkout 使用 App2Docker `--source local`，并保存文件 SHA-256 清单。
6. 构建完成后逐个执行 `docker buildx imagetools inspect <镜像>:<新标签>`，确认 AMD64/ARM64 清单，保存 OCI 索引摘要。不得用浮动标签直接更新 Swarm。

## 4. 环境发布顺序

整套环境升级按 **JBM → IoT → 建筑平台**处理依赖；只变更其中一个平台时仅滚动对应服务。每个服务先存旧 `docker service inspect`，再使用 `镜像@sha256:<摘要>` 更新，保持已有环境变量、密钥、挂载、网络、副本与更新策略。采集与规则服务按现有消费语义逐项滚动，防止双消费者重复处理。数据库迁移先在克隆库验证，再按该服务的启动/迁移机制执行。

每一步必须等副本、健康检查和关键业务指标稳定后继续。IoT 至少核对设备总数、在线/离线数量、MQTT/Kafka 消费、TDengine 写入错误/积压、真实设备最近上报和新增诊断接口；建筑核对 API/批处理与报表新鲜度；JBM 核对认证、租户项目权限、网关及登录。验收只读取真实设备数据，不为了探测而下发控制指令或伪造生产上报。

## 5. 发布清单与回滚

每个环境每次发布生成独立、不可覆盖的记录，建议路径为 `docs/releases/<日期>-<环境>-<主题>.md`；服务器保留 root 可读的发布目录。记录以下字段：

| 字段 | 必须记录的内容 |
| --- | --- |
| 环境与时间 | 域名、Swarm/Compose 集群、开始/完成时间、操作人 |
| 三平台版本 | 当前环境 JBM/IoT/建筑的源码 commit、Git 标签、构建任务、镜像标签、各服务实际 digest |
| 数据版本 | 三平台数据库 revision、变更 SQL/迁移、备份及校验值 |
| 切换前后 | 服务规格备份、镜像摘要、副本/健康、关键业务指标和异常 |
| 验收与回退 | 测试结果、真实业务只读核对、回退条件、旧摘要、最终状态 |

若设备离线激增、消息停滞/重复、数据库迁移失败或关键服务不健康，停止后续更新，按切换前的服务规格及固定摘要逐项回退。通常保留向后兼容的新增表/索引；恢复数据库会覆盖新业务数据，须单独评估。回退后仍需复核设备连接、消息消费和数据新鲜度，并把结果写入同一发布记录。

## 6. 每次执行的强制核对

- 构建任务显示的标签与计划版本逐字一致；所有服务共用该次预期标签，历史标签摘要没有漂移。
- 源码提交与 Git 标签、测试结果、迁移演练和备份均可追溯。
- Swarm 服务使用固定摘要；实际摘要与构建结果、发布记录一致。
- 三个平台在目标环境的当前版本都能从最新发布记录查到；局部升级也更新环境组合记录。
- 完成验收后才写“发布成功”；部分通过、待观察或回滚均明确记录。
