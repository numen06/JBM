# JBM 全系统 OpenAPI 文档中心与调试工作台

日期：2026-06-03  
根目录：`D:\workspaces\JBM7`  
目标：让 JBM 已采集/可访问的 OpenAPI 在认证后的管理端真正体现“接口情况”，包括服务、分组、路径、方法、认证/开放状态、请求参数、请求体、响应结构、示例、原始 OpenAPI、以及安全受控的内部接口测试。公开 `/docs` 与内部 apidoc 分离，只展示已发布的接入说明/开发者文档，不直接开放全系统接口目录。

本次改造是前后端一体改造，不能只做其中一端：

- 后端负责 OpenAPI Hub、数据表、同步/增量更新、接口生命周期、认证接口、发布快照、安全测试代理。
- 前端负责内部 `/api/docs` 文档与调试页面、接口选择、文档导出、公开 `/docs` 与内部 apidoc 分离展示、API 资源管理页联动、菜单/路由/导航接入。
- 数据库迁移、菜单种子、权限初始化、验证脚本和页面截图也属于本次闭环范围。

## 1. 实施约束

实施前先阅读并遵守：

- `.cursor/rules/utf8-windows.mdc`
- `.cursor/rules/java-direct-debug.mdc`
- `.cursor/rules/frontend-pagination.mdc`

关键约束：

- Windows 下所有新增/修改文件必须保持 UTF-8；不要用 PowerShell `>`、`>>`、无编码 `Set-Content`、无编码 `Out-File` 写项目文件。
- 先执行 `git status --short` 和必要的 `git diff`，不要回退已有改动。
- Java 调试优先使用 VS Code Java 直接启动或 `scripts\jbm_cluster_ops.py`，不要因为少量 Java 改动反复跑根级 Maven。
- Maven 只在改了 POM、跨模块依赖、需要局部编译/测试时使用，并限制到最小模块。
- 前端任何可能超过 50 条的列表、选择器、接口目录都必须分页、虚拟滚动或服务端分页，不能直接渲染全量 `v-for`。
- 本方案涉及管理端页面，完成后必须实际打开页面检查；截图保存到验证产物目录。
- 启动 Java/Spring/Maven 进程用于验证后，验证完成必须停止，除非用户明确要求保留运行。

## 2. 现状判断

当前已经存在两条相关链路：

1. API 资源治理链路  
   - 后端：`jbm-cluster-platform-center/src/main/java/com/jbm/cluster/center/controller/BaseApiController.java`
   - 服务：`jbm-cluster-common/jbm-cluster-common-mysql/src/main/java/com/jbm/cluster/common/mysql/service/impl/BaseApiServiceImpl.java`
   - 实体：`jbm-cluster-api/jbm-cluster-api-basic/src/main/java/com/jbm/cluster/api/entitys/basic/BaseApi.java`
   - 前端：`jbm-admin-vue/src/views/api/ApiRegistryList.vue`
   - 用途：维护 `base_api`，作为 RBAC、API Key 授权、开放/认证/日志策略的真源。

2. API 资源扫描链路  
   - 扫描：`jbm-cluster-common/jbm-cluster-common-basic/src/main/java/com/jbm/cluster/common/basic/configuration/resources/JbmApiResourceScan.java`
   - 构建：`jbm-cluster-common/jbm-cluster-common-basic/src/main/java/com/jbm/cluster/common/basic/configuration/apis/ApiBuild.java`
   - 接收：`jbm-cluster-platform-center/src/main/java/com/jbm/cluster/center/listener/ApiResourceScanHandler.java`
   - 现状：扫描 Spring `RequestMappingHandlerMapping` 后同步到 `base_api`，只有 path、method、service、controller/method、name/desc、contentType、isAuth、accessLog 等治理字段。

所以“API 资源管理没有体现接口情况”的根因不是没采集，而是采集结果落到了授权资源表，缺少完整 OpenAPI 文档层：

- 没有保存每个服务的原始 Swagger/OpenAPI spec。
- 没有统一解析参数、requestBody、responses、schemas、examples。
- 公开 `/docs` 当前是手写 Wiki，不是由系统真实接口驱动。
- 管理端 `ApiRegistryList.vue` 是治理页，不适合承载完整文档和调试体验。

## 3. 方案选择

采用成熟现代 OpenAPI 工具链，而不是自研文档渲染器。

## 3.0 技术路线总览

本项目按“后端 OpenAPI Hub + JBM 原生文档体验 + base_api 治理联动”的路线实现。第三方文档组件只能作为可替换渲染器候选，必须先验证样式可控性；如果无法与 JBM 管理台风格一致，就使用自研原生文档视图。

### 3.0.0 管理归属

OpenAPI 文档中心统一放在 Center 中管理。

| 组件 | 职责 | 是否管理 apidoc |
|---|---|---|
| Center | OpenAPI Hub、文档存储、同步任务、operation 索引、发布快照、管理端接口、测试代理入口 | 是 |
| Gateway | 路由、认证、签名、API Key、限流、日志；为 Center 同步/测试提供统一访问路径 | 否 |
| 各业务应用 | 暴露 `/v2/api-docs` 或 `/v3/api-docs`，启动后上报 `base_api` 资源 | 否 |
| Admin Vue | 调用 Center 的 `/api-docs/**` 管理接口展示和操作 | 否 |

操作方式：

1. 各应用启动后，现有 `JbmApiResourceScan` 继续把基础接口资源上报到 Center，Center 写入/更新 `base_api`。
2. 管理员登录管理端，进入 `API管理 / API文档与调试`，前端调用 Center 的 `/api-docs/**`。
3. Center 通过 Gateway 或 Discovery 拉取各应用的 Swagger/OpenAPI spec，解析后写入 `open_api_document` 和 `open_api_operation`。
4. Center 按 `serviceId + path + method` 关联 `base_api`，把“接口结构”和“治理状态”合并展示。
5. 在线测试由前端调用 Center 的 `/api-docs/test`，Center 校验权限和 operation 后再经 Gateway 转发。
6. 公开 `/docs` 不读内部 apidoc；需要对外展示时，由 Center 从内部文档生成 `published_api_doc` 快照，公开页只读快照。

实现时不要把 OpenAPI Hub 放到 Gateway，也不要让每个业务服务自己管理文档目录。Gateway 可以提供聚合访问路径，但管理、存储、发布、测试授权都归 Center。

### 3.0.1 分层职责

```text
各业务服务
  负责暴露 /v2/api-docs 或 /v3/api-docs
  继续通过现有 JbmApiResourceScan 上报 base_api 授权资源

Center OpenAPI Hub
  负责拉取、解析、存档、索引、过滤、测试代理
  负责把 OpenAPI operation 与 base_api 治理状态关联

Gateway
  继续负责路由、认证、API Key、签名、限流、日志
  管理端测试请求默认经 Gateway 转发，不绕过治理链路

Admin Vue
  内部 /api/docs 使用 JBM 原生界面展示全量文档和安全调试，必须登录并具备菜单权限
  可选嵌入 Scalar，但必须通过样式验收；不达标则不用
  公开 /docs 只展示独立发布的开发者文档，不直接读取 /api-docs/**
```

### 3.0.2 数据真源划分

| 数据 | 真源 | 说明 |
|---|---|---|
| 接口治理状态 | `base_api` | `status`、`isOpen`、`isAuth`、`accessLog`、API Key 授权依旧以这里为准 |
| 接口结构文档 | OpenAPI spec | 参数、请求体、响应、schema、example 来自 `/v2/api-docs` 或 `/v3/api-docs` |
| 文档索引 | `open_api_operation` | 便于搜索、过滤、关联治理状态和公开过滤 |
| 原始文档 | `open_api_document.raw_spec` | Scalar 渲染和问题排查使用 |
| 在线测试 | `/api-docs/test` 代理 | 不让前端直接打任意 URL，后端根据 operation 受控转发 |
| 公开文档 | `published_api_doc` 或前端静态内容 | 与内部 apidoc 分离，只展示被人工/流程发布的内容 |
| 导出文档 | `open_api_export_task` 或同步导出响应 | 从内部认证文档中心选择接口后导出，不对公开页面开放 |

### 3.0.3 推荐技术栈

后端：

- `swagger-parser`：解析 Swagger 2/OpenAPI 3。
- Spring `DiscoveryClient`：发现服务实例。
- 现有 Gateway 路由：优先通过 Gateway 拉取 spec 和执行测试。
- 现有 MyBatis/MasterData 风格：新增 mapper/service/entity，不引入新的 ORM。

前端：

- 现有 Vue 3 + Pinia + Axios + UI 组件：承载筛选、同步、测试、治理状态卡片和原生文档详情。
- `@scalar/api-reference`：仅作为可选 Reference 预览候选，不作为默认正式页面依赖。
- 若使用 Scalar，必须隐藏或禁用其原生测试能力，统一使用 JBM 自定义安全测试面板。

路线原则：

- 不重写现有 API 资源管理。
- 不直接在前端解析大 OpenAPI JSON 做复杂筛选，筛选索引由后端给。
- 不把文档结构塞进 `base_api`，避免污染授权治理表。
- 不强制 Springdoc 迁移，先兼容当前 Springfox `/v2/api-docs`。
- 不把内部 `/api-docs/**` 作为公开接口；公开 `/docs` 只能消费已发布文档快照或静态内容。

### 3.1 前端文档渲染策略

默认策略：优先做 JBM 原生文档视图，第三方组件只作为可验证候选。

原因：

- JBM 管理台已经有自己的页面结构、表格、Badge、Button、Dialog、PaginationBar、PageHeader 等组件。
- API 文档页不仅是阅读器，还包含治理状态、选择导出、发布快照、安全测试、资源管理跳转，第三方组件很难完整承载。
- 自研视图可以确保风格、交互、权限、分页和导出都与系统一致。

第三方候选：

- `@scalar/api-reference`：可作为右侧 Reference 预览候选。
- Swagger UI：只作为后备调研，不作为默认方案。
- Stoplight Elements：只作为后备调研，不作为默认方案。

第三方组件准入标准：

- 能关闭或覆盖默认主题，使整体视觉贴合 JBM 管理台。
- 能使用 JBM 的字体、间距、颜色、border、radius、暗色/亮色变量。
- 能隐藏原生 Try It，并接入 JBM 自己的安全测试面板。
- 能按当前服务/operation 定位，不破坏管理台布局和滚动。
- 移动端和窄屏不溢出，不产生与 JBM 导航/抽屉冲突的浮层。
- 能通过浏览器截图验收。

如果任一关键项不满足：

- 不引入第三方渲染器到正式页面。
- 使用 JBM 原生视图渲染 operation 详情。
- 仍可保留导出 OpenAPI JSON 供外部 Swagger/Scalar 工具离线使用。

JBM 原生文档视图最低实现：

- 左侧接口目录：服务、tag、method、path、summary、治理状态、分页/虚拟滚动。
- 右侧接口详情：概览、认证/开放状态、参数表、请求体 schema、响应 schema、示例、原始 JSON。
- 底部/抽屉：安全测试、导出、发布、跳转 API 资源管理。

### 3.2 后端解析器

选择：`io.swagger.parser.v3:swagger-parser`

原因：

- Java 生态成熟。
- 可读取 JSON/YAML OpenAPI。
- 可将 Swagger/OpenAPI 2.0 转为可处理的 OpenAPI 3 模型。
- 支持解析、校验、resolve/flatten 等能力。

### 3.3 Springfox/Springdoc 策略

第一阶段不强制迁移 Springfox。

当前 JBM 是 Spring Boot `2.6.4`，已有 Springfox `3.0.0` 和 `/v2/api-docs`。本轮优先聚合现有 `/v2/api-docs`，并兼容未来 `/v3/api-docs`。后续可单独开计划逐服务迁移到 Springdoc，但不要把迁移 Springdoc 作为本计划的前置条件。

职责：

- `OpenApiHubService`
  - 拉取或接收 spec。
  - 调用 `swagger-parser` 解析。
  - 存储 `OpenApiDocument`。
  - 展开 paths/operations。

- `OpenApiSpecSanitizer`

  - 接收内部 `/api-docs/publish` 发布请求。

- `OpenApiTestProxyService`
  - 只允许测试已存在的 operation。
  - 禁止任意 URL 转发。
  - 只允许经 Gateway 或配置好的服务地址调用。

### 5.5 同步来源

第一阶段来源：

- 从服务发现或配置里得到 `serviceId`。
- 优先尝试 `/{serviceId}/v2/api-docs` 经 Gateway 拉取。
- 可选兼容 `/{serviceId}/v3/api-docs`。

建议调用顺序：

1. Gateway 聚合路径：`http://127.0.0.1:7777/{serviceId}/v2/api-docs`
2. 服务直连地址：从 DiscoveryClient 获取 instance URI 后拼 `/v2/api-docs`
3. 手动配置 sourceUrl：后续增强，不作为首版必须项

失败处理：

- 单个服务同步失败不影响其他服务。
- `OpenApiDocument.syncStatus=FAILED`，`syncMessage` 保存摘要。
- 前端 sources 列表显示失败服务和最近错误。

## 7. 安全边界

必须实现：

- `/api-docs/**` 全部需要认证和菜单权限；不能因为要给 Scalar 读取 spec 就放开。
- 公开 `/docs` 不直接读取内部 apidoc，只读取已发布文档快照或静态文档内容。
- 发布快照如果包含 API 摘要，只能展示发布时确认允许对外展示的接口；最低过滤条件是 `base_api.status=1 && base_api.is_open=1`，但满足这个条件也不代表自动发布。
- 公开文档不展示内部接口、未关联开放资源的 operation、停用资源、未发布的新接口。
- 在线测试只在管理端开放。
- `POST /api-docs/test` 只接受 `operationId` 或 `serviceId + path + method`，不接受任意 URL。
- `GET/HEAD/OPTIONS` 可直接测试。
- `POST/PUT/PATCH/DELETE` 必须携带 `confirm=true`；前端必须二次确认。
- 测试代理默认经 Gateway 调用，避免绕过认证、限流、日志和网关策略。
- 测试请求超时建议 10 秒，响应 body 截断展示，避免大响应拖垮页面。
- 不记录或回显敏感 header：`Authorization`、`Cookie`、`X-JBM-Signature`、`secretKey`、`privateKey`。

不做：

- 不在公开 `/docs` 提供在线 Try It。
- 不公开 `/api-docs/sources`、`/api-docs/spec/{serviceId}`、`/api-docs/operations`。
- 不允许用户输入任意目标 URL 进行代理。
- 不把 `base_api` 扩成大 JSON 文档表。
- 不在本轮迁移所有服务到 Springdoc。

## 8. 数据流

### 8.1 同步数据流

```text
1. 应用启动后现有 JbmApiResourceScan 上报 API 资源，或管理员点击“同步文档”，或系统定时触发
2. Center OpenApiHub 获取服务列表
   - 来源 A：DiscoveryClient
   - 来源 B：Gateway route/serviceId
   - 来源 C：手动配置 sourceUrl，作为后续增强
3. 对每个 serviceId 拉取 spec
   - 优先 GET http://gateway/{serviceId}/v2/api-docs
   - 失败后尝试 /v3/api-docs
   - 再失败时可尝试服务实例直连 /v2/api-docs
4. swagger-parser 解析 spec
5. 保存 open_api_document
   - rawSpec 保存原始 JSON
   - sourceHash 判断是否变化
   - syncStatus 记录 SUCCESS/FAILED
6. 展开 paths[*][method] 为 open_api_operation
7. 关联 base_api
   - 匹配键：serviceId + normalizedPath + requestMethod
   - 命中后写 apiId、isOpen、isAuth、status
   - 未命中则保留 operation，但标记“未关联 API 资源”
8. 对比上一版本 operation 快照，计算新增、变更、消失
9. 前端 sources 和 operations 查询读 OpenAPI Hub
```

同步结果示例：

```json

  "syncStatus": "SUCCESS",
  "operationTotal": 128,
  "linkedApiTotal": 116,
  "unlinkedApiTotal": 12,
  "sourceHash": "sha256:...",
  "syncTime": "2026-06-03T18:30:00"
}
```

### 8.1A 应用重启后的接口生命周期

每次应用重启都可能扫描到新接口，处理规则必须是“内部自动发现，治理状态保留，公开文档不自动发布”。

接口状态建议：

| 状态 | 触发条件 | 处理 |
|---|---|---|
| `NEW` | 本次同步首次出现 | 插入 `open_api_operation`，尝试关联/创建 `base_api`，默认只进入内部文档 |
| `ACTIVE` | 本次同步仍存在 | 更新摘要、schema、hash、`lastSeenTime`，保留 `base_api` 治理状态 |
| `CHANGED` | path/method 相同但 schema/hash 变化 | 更新 operation 内容，记录 `sourceHash`，前端标记“有变更” |
| `MISSING` | 上次存在，本次 spec 中消失 | 不物理删除，标记下线/消失，默认从活动列表隐藏，可在“已下线接口”筛选查看 |
| `FAILED` | 服务 spec 拉取或解析失败 | 保留上次成功版本，sources 显示同步失败和错误摘要 |

新增接口处理：

- `JbmApiResourceScan` 仍负责把接口治理资源同步到 `base_api`。
- 如果扫描到新接口，`base_api` 默认 `isOpen=0`、`status=1`、`isPersist=true`，不得自动对外开放。
- OpenAPI Hub 同步到新 operation 后，内部 `/api/docs` 可立即看到“新增接口”。
- 新接口是否进入公开 `/docs`，必须由管理员在内部页面执行“发布文档”或后续发布流程确认。

变更接口处理：

- `serviceId + path + requestMethod` 不变时，认为是同一个 operation。
- 参数、请求体、响应 schema 变化时更新 `open_api_operation`，保留 `apiId` 和 `base_api` 治理状态。
- 前端在内部 `/api/docs` 标记“最近变更”，方便管理员复核。

下线接口处理：

- 不立即删除 `open_api_operation` 和 `base_api`，避免误删权限历史和测试记录。
- `open_api_operation.syncState=MISSING`，记录 `removedTime`。
- 活动接口列表默认隐藏 `MISSING`，但可通过筛选查看。
- 是否清理 `base_api` 或权限关系，必须由管理员确认或单独清理任务执行。

公开发布处理：

- 服务重启产生的新接口不会自动进入公开 `/docs`。
- 公开文档只读取 `published_api_doc` 快照或静态 `apiWikiContent.ts`。
- 管理员在 `/api/docs` 复核接口后，点击“发布文档”生成快照。
- 发布快照保存 `publishedVersion`、`publishedAt`、`publisherUserId`、`sourceHash`，便于回滚和追踪。

### 8.6 接口选择、导出与发布数据流

内部 `/api/docs` 必须支持选择接口后导出文档。导出是认证后的内部能力；发布是把经过选择和过滤的内容生成公开快照，两者不能混为一谈。

选择范围：

| 选择方式 | 说明 |
|---|---|
| 当前服务全部接口 | 导出某个 `serviceId` 下所有当前筛选可见接口 |
| Tag/分组 | 按 OpenAPI tag 或业务分组导出 |
| 搜索/筛选结果 | 按 keyword、method、isOpen、isAuth、syncState、linked 等筛选后导出 |
| 手动勾选 | 在接口目录中勾选 operation，导出精确接口集合 |
| 已发布集合 | 复用某个 `published_api_doc` 的接口集合重新导出 |

导出格式：

| 格式 | 文件类型 | 用途 |
|---|---|---|
| OpenAPI JSON | `.json` | 给工具链、SDK 生成器、Scalar/Swagger UI 使用 |
| OpenAPI YAML | `.yaml` | 给开发者阅读和版本管理 |
| Markdown | `.md` | 进入项目文档、评审、轻量分享 |
| HTML | `.html` 或 `.zip` | 离线可浏览文档包，适合交付 |
| Postman Collection | `.json` | 导入 Postman 调试 |
| curl 示例包 | `.zip` 或 `.md` | 每个接口生成 curl 示例 |

首版推荐实现：

- 必做：OpenAPI JSON、Markdown、HTML。
- 可选：OpenAPI YAML、Postman Collection、curl 示例包。
- PDF 不作为首版必做；如必须支持，建议先 HTML 导出，再后续引入受控 PDF 渲染。

导出请求示例：

```json
{
  "format": "MARKDOWN",
  "selectionMode": "CHECKED",
  "serviceIds": ["jbm-cluster-platform-center"],
  "operationIds": [10001, 10002],
  "filters": {
    "method": "GET",
    "isOpen": 1,
    "syncState": "ACTIVE"
  },
  "includeSchemas": true,
  "includeExamples": true,
  "includeGovernance": true
}
```

导出处理：

```text
用户选择接口
  -> POST /api-docs/export
  -> Center 校验登录、菜单权限、operation 可见性
  -> 根据 selectionMode 解析最终 operationIds
  -> 从 open_api_document/open_api_operation/base_api 组装导出模型
  -> 按 format 生成文件
  -> 小文件同步返回下载流
  -> 大文件创建 OpenApiExportTask，前端轮询 GET /api-docs/export/{taskId}
```

导出内容必须包含：

- 服务名、文档版本、导出时间、导出人。
- 每个接口的 method、path、summary、description、tag。
- 参数表：path/query/header/body。
- 请求体 schema 和示例。
- 响应状态码、响应 schema 和示例。
- 治理状态：是否开放、是否认证、是否启用、是否关联 `base_api`。

导出内容不能包含：

- 内部 token、secret、privateKey。
- 用户当前 Authorization/Cookie。
- 未被选择的接口。
- 公开导出时未发布的接口。

发布数据流：

```text
用户选择接口
  -> 点击“发布为公开文档”
  -> Center 按最低条件过滤 status=1 && isOpen=1 && linked=true
  -> 用户确认标题、版本、说明
  -> POST /api-docs/publish
  -> Center 生成 published_api_doc 快照
  -> /docs 只读取 published_api_doc 或静态内容
```

导出和发布的区别：

- 导出：内部能力，可以包含内部接口和治理状态，文件给团队使用。
- 发布：公开能力的来源，只能包含确认允许外部看到的接口或说明，且不会自动随应用重启变化。

- 分 Tab 展示：概览、请求参数、请求体、响应、示例、原始 JSON。

- 如果第三方 Reference 通过样式验收，可增加“Reference 预览”Tab，但不能替代 JBM 原生详情和治理操作。

  [去 API资源管理]

- Query Params 表单。

- POST/PUT/PATCH/DELETE：显示二次确认提示，用户确认后发送。

导出/发布面板：

### 8A.4 空状态与异常状态
