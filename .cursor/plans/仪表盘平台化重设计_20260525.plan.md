# JBM 管理台仪表盘平台化重设计计划

## 背景判断

当前 `jbm-admin-vue/src/views/dashboard/DashboardPage.vue` 的仪表盘主要由三部分组成：用户总数、在线用户、快捷入口，以及一块 jaja7 本地环境说明。它更像开发联调说明页，不像平台控制台首页。

结合现有系统，JBM 管理台已经具备以下平台化基础：

- 前端已按 `系统管理 / 权限管理 / API 管理 / 网关管理 / 开放平台` 组织导航。
- 登录后通过 `/current/user/menus` 获取当前用户菜单，`menuStore.isRouteAllowed()` 已用于路由守卫和快捷入口过滤。
- `usePermission()` 已支持 `MENU_*`、`ACTION_*` 权限判断，并内置超管识别。
- 后端 RBAC 已抽象 `menu / action / api` 三类权限资源，支持角色授权、用户直授、应用授权和多应用菜单隔离。
- 现有 API 已有部分仪表盘可用数据：`/user/statistics`、`/gateway/discovery/services`、网关路由分页、限流策略分页、IP 策略分页、API 资源/权限目录等。

因此新仪表盘不应继续堆环境说明，而应成为“按角色呈现的平台工作台”：不同角色只看到自己有权限访问的运营概览、治理入口、待办风险和自助能力。

## 目标

将仪表盘重设计为平台化首页，第一屏回答四个问题：

1. 当前登录身份是谁，属于哪个角色/应用上下文。
2. 我能管理哪些平台能力。
3. 当前平台运行和治理状态是否正常。
4. 我下一步最可能要处理什么。

同时确保：

- 所有卡片、指标、入口都尊重角色权限。
- 不因仪表盘聚合接口泄露未授权模块的数据。
- 自助开发者、普通管理者、平台超管看到的首页重点不同。
- 环境说明迁移到文档或开发模式提示，不占据正式仪表盘主视觉。

## 角色视角设计

### 1. 平台超管 / super_admin / admin

可见完整平台驾驶舱：

- 系统概览：用户总数、在线用户、应用数、组织数。
- 权限治理：角色数、权限资源数、未绑定菜单/按钮/API 的风险提示。
- API 与开放平台：API 总数、受保护 API、开放 API、API Key 数。
- 网关治理：注册服务数、健康实例数、路由数、限流策略数、IP 策略数。
- 安全审计：最近登录、在线会话、审计日志入口。
- 平台维护快捷入口：菜单与按钮、权限目录、角色管理、API 资源管理、服务发现、路由管理。

### 2. 系统管理员

可见与用户、组织、角色和基础资料相关内容：

- 用户总数、在线用户。
- 用户管理、组织管理、角色管理、字典管理、扩展字段入口。
- 权限风险只显示其有权限管理的范围，例如用户授权、角色授权。
- 不显示 API、网关、开发者相关指标，除非菜单授权允许。

### 3. 网关 / 运维管理员

可见运行治理工作台：

- 注册服务数、健康实例数、异常服务数。
- 路由数、启用路由数、限流策略数、IP 策略数。
- 服务发现、路由管理、限流策略、IP 限制、灰度发布入口。
- API 监控若仍是占位页，不应在仪表盘中包装成已可用能力。

### 4. API / 开放平台管理员

可见开放平台工作台：

- API 资源数、需要认证 API、公开 API、API Key 数。
- API 资源管理、客户端权限、开发者、API Key、API Wiki 入口。
- 权限目录中 API 相关风险，例如 API 资源无权限点、权限点残留等，后端支持前先作为二期。

### 5. 普通开发者 / 自助用户

只可见自助接入首页：

- 当前开发者身份。
- API Key 入口。
- API Wiki 入口。
- 开发者认证状态。
- 不显示用户总数、在线用户、网关、权限管理等平台管理数据。

## 信息架构

### 第一屏：身份与平台状态

建议结构：

```text
仪表盘
  当前身份摘要
  平台状态指标卡
  权限可见的快捷入口
```

身份摘要内容：

- 登录名 / 昵称。
- 角色名称。
- 当前 clientId / appId，如果后端当前用户模型补齐。
- 当前可见菜单数量。

状态指标卡按权限动态出现：

- `MENU_user` / `/system/users`：用户总数。
- `MENU_onlineUsers` / `/system/online-users`：在线用户。
- `MENU_apps` / `/system/apps`：应用数。
- `MENU_api_registry` / `/api/registry`：API 资源数。
- `MENU_gw_services` / `/gateway/services`：服务数、健康实例数。
- `MENU_gw_routes` / `/gateway/routes`：路由数。
- `MENU_gw_rate` / `/gateway/rate-limit`：限流策略数。
- `MENU_account_logs` / `/log/account`：审计日志入口，不先做日志数量，避免无接口时硬凑。

### 第二屏：治理工作台

按模块展示可见工作区：

```text
系统治理
权限治理
API 治理
网关治理
开放平台
```

每个工作区只在存在至少一个可访问入口时展示。工作区内用小型列表或紧凑操作按钮，不做大面积营销式卡片。

### 第三屏：待办与风险

一期不新增复杂风险接口，只做轻量提示：

- 菜单数据加载失败：提示重新登录或检查 `/current/user/menus`。
- 没有后台菜单，仅有自助入口：显示开发者自助工作台。
- 服务发现接口失败：只在有网关权限时提示“服务发现不可用”，不要影响其他区域。
- API 监控仍为规划页时，仪表盘不展示监控趋势图，只展示“待接入指标”状态。

二期再引入后端风险聚合：

- 无权限点的菜单/按钮/API。
- 已授权但资源不存在的孤儿权限。
- 无健康实例但仍启用的路由。
- 公开 API 数量异常。
- 过期或即将过期的应用授权/API Key。

## 权限设计原则

### 前端显示权限

前端必须使用现有能力统一判断：

- 页面入口：`menuStore.isRouteAllowed(path)`。
- 菜单编码：`menuStore.allowedMenuCodes`。
- 细粒度动作：`usePermission().hasAction(actionCode)`。
- 超管兜底：`usePermission().isSuperAdmin`。

仪表盘中任何 RouterLink 都必须经过 `isRouteAllowed()` 过滤。任何来自管理接口的指标卡，也必须先判断对应模块是否可访问。

### 后端数据权限

如果新增聚合接口，不能仅靠前端隐藏：

- 新增 `GET /dashboard/overview` 或 `GET /current/dashboard` 时，后端必须基于 `LoginHelper.getUserId()`、`JbmLoginUser.appId`、角色权限和菜单权限计算可返回字段。
- 返回结构中建议带 `permissions` 或 `sections`，让前端知道哪些分区可展示。
- 普通开发者不返回用户总数、在线用户、应用总数、网关状态等平台级指标。
- 多应用场景下，统计必须按当前 `appId` 过滤；平台公共数据需明确标记。

### 权限映射建议

```text
系统概览      -> /system/users, /system/online-users, /system/orgs, /system/apps
权限治理      -> /authority/roles, /authority/user-permissions, /authority/client-permissions, /authority/catalog, /system/menus
API 治理      -> /api/registry, /api/monitor
网关治理      -> /gateway/services, /gateway/routes, /gateway/rate-limit, /gateway/ip-limit, /gateway/gray-release
开放平台      -> /developer, /developer/api-keys, /docs
审计安全      -> /log/account, /system/online-users
```

## 数据方案

### 一期：复用现有接口，前端组合

优先不动后端，用现有接口构建平台化体验：

- `getUserStatistics()`：用户总数、在线用户。
- `listDiscoveryServices()`：服务数、健康实例数。
- `listRoutes(1, 1)`：路由总数。
- `listRateLimits(1, 1)`：限流策略总数。
- `listIpLimits(1, 1)`：IP 策略总数。
- `menuStore.rawMenus`：当前可见菜单数量和工作区可见性。
- `auth.user.roles` / `auth.user.authorities`：身份摘要。

注意事项：

- 每个接口只在对应 route 允许时调用。
- 某个接口失败时只降级对应卡片，不让整个仪表盘失败。
- 网关服务发现可能依赖 Nacos，失败时显示“不可用”而不是 0。
- `API 监控` 当前是规划占位，不做假数据趋势。

### 二期：新增后端聚合接口

建议新增：

```text
GET /current/dashboard
```

或：

```text
GET /dashboard/overview
```

推荐返回：

```json
{
  "identity": {
    "userId": 1,
    "userName": "admin",
    "nickName": "管理员",
    "roles": ["super_admin"],
    "appId": 1,
    "clientId": "demo"
  },
  "sections": {
    "system": true,
    "authority": true,
    "api": true,
    "gateway": true,
    "developer": true,
    "audit": true
  },
  "metrics": {
    "usersTotal": 12,
    "onlineUser": 2,
    "serviceCount": 6,
    "healthyInstanceCount": 6,
    "routeCount": 8,
    "apiCount": 120,
    "apiKeyCount": 4
  },
  "risks": [
    {
      "level": "warning",
      "title": "存在无健康实例的启用路由",
      "target": "/gateway/routes"
    }
  ]
}
```

接口实现位置建议：

- `jbm-cluster-platform-center` 中新增 `DashboardController`。
- 只聚合 Center 可直接拿到的数据。
- 网关运行态或 Nacos 数据如果从 Center 获取成本高，先由前端调用现有网关治理接口，不强行塞入一期后端。

## 前端实施计划

### 1. 新建仪表盘配置层

建议新增文件：

- `jbm-admin-vue/src/views/dashboard/dashboardSections.ts`

职责：

- 定义工作区、指标卡、快捷入口的元数据。
- 每项绑定 `path`、`menuCodes`、`actionCodes`、图标、标题、说明。
- 提供过滤函数，集中处理权限判断。

这样 `DashboardPage.vue` 不堆大量硬编码判断，后续新增模块也清晰。

### 2. 新建仪表盘数据 API 封装

一期可新增：

- `jbm-admin-vue/src/api/dashboard.ts`

职责：

- `loadDashboardOverview()`：按权限并行加载现有接口。
- 每个分区独立 try/catch。
- 返回统一的 `DashboardMetric[]`、`DashboardSection[]`、`DashboardNotice[]`。

若后续新增 `/current/dashboard`，这个文件可以无痛切换为优先调用聚合接口。

### 3. 重构 `DashboardPage.vue`

目标布局：

```text
PageHeader：仪表盘 / 当前角色和平台上下文

身份与状态条
  当前用户
  角色
  可见模块数
  菜单加载状态

关键指标区
  按权限展示 2 到 8 个紧凑指标卡

工作区入口
  系统治理
  权限治理
  API 治理
  网关治理
  开放平台

待办与风险
  权限/接口/服务发现的降级提示
```

UI 要求：

- 保持管理后台风格，信息密度适中，不做营销 hero。
- 去掉大段环境说明。
- 快捷入口不要铺成一大堆按钮，应按工作区分组。
- 卡片半径沿用现有 `Card`，不要嵌套卡片。
- 指标失败时展示 `—` 或状态 Badge，并显示简短原因。
- 移动端单列，桌面端 3 到 4 列指标网格。

### 4. 自助用户体验

当用户只有 `SELF_SERVICE_PATHS`：

- 首页标题仍为“仪表盘”。
- 展示“开放平台工作台”。
- 只显示开发者认证、API Keys、API Wiki。
- 不调用 `/user/statistics`。
- 不出现系统治理、权限治理、网关治理指标。

### 5. 环境说明迁移

现有 jaja7 环境说明不建议继续放仪表盘主页面。

处理方式：

- 移到 `docs` 或 `.cursor/plans` 的运维说明。
- 或在开发环境下折叠显示，例如仅 `import.meta.env.DEV` 展示“本地联调提示”。
- 正式 UI 中不默认展开。

## 后端实施计划（二期）

### 1. 新增仪表盘 DTO

建议包路径：

- `jbm-cluster-api-basic/.../model/dashboard/`

DTO：

- `DashboardOverview`
- `DashboardIdentity`
- `DashboardMetric`
- `DashboardSection`
- `DashboardRisk`

### 2. 新增 Controller

建议位置：

- `jbm-cluster-platform-center/src/main/java/com/jbm/cluster/center/controller/DashboardController.java`

接口：

```text
GET /current/dashboard
```

鉴权：

- `@SaCheckLogin`
- 内部使用当前登录用户上下文，不允许传 userId 查询他人仪表盘。

### 3. 指标权限裁剪

后端聚合逻辑必须按权限裁剪：

- `usersTotal` 仅有用户管理或超管可见。
- `onlineUser` 仅有在线用户或审计相关权限可见。
- `apiCount` 仅有 API 管理权限可见。
- `routeCount`、`serviceCount` 仅有网关管理权限可见。
- `authorityRisk` 仅有权限管理权限可见。

### 4. 多应用隔离

指标默认按 `JbmLoginUser.appId` 过滤：

- 菜单：当前应用 + 公共菜单。
- 用户、角色、API、应用授权等若底层实体有 `appId`，必须按当前应用过滤。
- 平台超管可以看到平台汇总，但返回中要标记 `scope: platform`。

## 验收标准

### 权限验收

- 普通自助用户登录后，仪表盘不请求 `/user/statistics`，不显示用户总数、在线用户、网关、权限管理入口。
- 只有用户管理权限的用户，看不到网关和 API 治理指标。
- 只有网关权限的用户，看不到用户总数和角色授权入口。
- 超管可以看到所有工作区和完整快捷入口。
- 手动访问未授权路由仍被 `router.beforeEach` 重定向回仪表盘。

### 体验验收

- 第一屏能看到身份、角色、主要状态和可用工作区。
- 环境说明不再占据正式仪表盘主区域。
- 某个模块接口失败不会拖垮整个仪表盘。
- 快捷入口按模块分组，不出现用户无权访问的链接。
- 桌面和移动端无文本溢出、重叠、按钮挤压。

### 数据验收

- 用户统计来自 `/user/statistics`。
- 服务数与健康实例来自 `/gateway/discovery/services`。
- 路由、限流、IP 策略总数来自分页接口的 `total`。
- 没有真实接口的数据不显示假图表。
- API 监控在指标接口完成前只显示“待接入”状态，不展示伪趋势。

## Cursor 执行建议

建议 Cursor 按以下顺序执行：

1. 阅读 `DashboardPage.vue`、`menu.ts`、`auth.ts`、`usePermission.ts`、`adminNav.ts`，确认现有权限判断方式。
2. 新增 `dashboardSections.ts`，把工作区、指标、快捷入口抽成配置。
3. 新增 `api/dashboard.ts`，按权限加载现有统计接口，每个模块独立降级。
4. 重构 `DashboardPage.vue` 为平台工作台布局，移除默认展开的环境说明。
5. 确认自助用户只展示开放平台入口，不调用管理统计接口。
6. 跑前端类型检查和构建。
7. 用超管、系统管理员、网关管理员、自助用户四类账号做浏览器验证。
8. 二期再做 `/current/dashboard` 后端聚合接口和风险提示，不要在一期伪造不可验证数据。
