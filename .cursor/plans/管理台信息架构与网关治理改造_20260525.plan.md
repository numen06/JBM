# 管理台信息架构与网关治理改造设计方案

## 背景

当前系统已经集成 Spring Cloud Alibaba、Nacos、Spring Cloud Gateway、动态 DB 路由、限流表、网关管理页面等能力，但管理台的使用体验更像“路由配置 CRUD”。它没有把 Nacos 注册中心、服务实例、健康状态、灰度发布、动态路由刷新和运行态诊断串成一个真正可用的集群治理闭环。

同时，当前“菜单管理”和“按钮管理”被拆成两个独立入口，并放在“其他”分组里，不符合 RBAC 的真实逻辑。底层模型中 `BaseAction.menuId` 已经表明按钮属于菜单，`BaseAuthority` 又把菜单、按钮、API 统一抽象成权限点。因此前端信息架构应改为“权限管理 -> 菜单与按钮”，授权页面也应继续以菜单树组织按钮权限。

本方案目标：

- 把菜单、按钮、权限目录、角色/用户授权重新放回同一个权限管理语义下。
- 把网关模块从“摆设型配置页”改造成“服务治理型网关控制台”，参考阿里系 Nacos / Spring Cloud Alibaba 的管理模式，优先做实路由转发、服务发现、灰度上线和运行态诊断。

本阶段只写方案，不做回测。实现完成后再一起联调测试。

## 当前判断：权限管理

### 已经具备的能力

- 后端模型中按钮动作 `BaseAction` 已通过 `menuId` 归属于菜单。
- 权限点统一落在 `BaseAuthority`，通过 `resourceType=menu/action/api` 区分资源类型。
- 角色授权页 `RoleList.vue` 已按“菜单 -> 按钮”展示权限。
- 用户授权页 `UserPermissionList.vue` 已按“菜单 -> 按钮”展示权限。
- 权限目录 `AuthorityCatalog.vue` 已能展示菜单、按钮、API 三类权限。

### 主要问题

- “菜单管理”和“按钮管理”当前在导航上被放到“其他”，从产品语义上脱离权限管理。
- “按钮管理”作为独立一级页面存在，会让用户误以为按钮可以脱离菜单独立管理。
- 菜单页和按钮页割裂，新增按钮时需要跨页面理解所属菜单。
- 权限目录中菜单和按钮是分 tab 并列展示，缺少“按钮归属菜单”的结构感。
- API 注册中心页面目前更像“接口目录展示”，不是真正 API 管理：
  - 前端调用 `/authority/apis` 或 `/authority/resources` 全量拉取后做本地分页。
  - 缺少后端分页、服务筛选、路径筛选、状态筛选、认证/开放状态筛选。
  - 缺少新增、编辑、删除、启停、批量操作等管理动作。
  - 缺少与限流、IP 策略、API Key 授权的直接操作入口。
  - 分组视图每组只展示前 50 条，接口量大时容易误导。
- 角色/用户授权页虽然结构基本正确，但交互上缺少父子联动：
  - 勾选按钮时应自动勾选所属菜单。
  - 取消菜单时应提示或同步取消其下按钮。
  - 半选状态没有体现。
- 导航命名存在重复概念：
  - “权限目录”偏审计/查看。
  - “菜单管理 / 按钮管理”偏资源维护。
  - 二者应在“权限管理”下形成闭环。

## 当前判断：网关治理

### 已经具备的能力

- Gateway 使用 Spring Cloud Gateway。
- 项目已经接入 Spring Cloud Alibaba / Nacos。
- `GatewayRouteServiceImpl#getMicroServices()` 已能通过 `DiscoveryClient#getServices()` 获取注册服务。
- `gateway_route` 表会被 `JdbcRouteDataSource` 读取。
- `DynamicRouteDefinitionLocator` 会将 DB 路由加载到 `InMemoryRouteDefinitionRepository`。
- Center 在新增、修改、删除路由后会调用 `JbmClusterTemplate#refreshGateway()` 广播 `RemoteRefreshRouteEvent`。
- Gateway 监听 `RemoteRefreshRouteEvent` 后会触发动态路由刷新。
- 限流已有 `gateway_rate_limit`、`gateway_rate_limit_api` 和 `RequestRateLimiter` 的实现基础。

### 主要问题

- 管理台没有真正展示 Nacos 服务实例、健康状态、metadata、cluster、权重等注册中心信息。
- 路由创建仍以手填为主，没有围绕“注册服务”来建模。
- 灰度发布缺少数据模型和 Gateway 执行逻辑。
- 动态路由刷新只看到 `save`，没有明确清理旧路由，删除或停用路由后可能出现运行态残留。
- 网关页面没有运行态诊断能力，管理员无法确认路由是否真的发布、是否有健康实例、实际命中了哪个服务。
- 现在的“路由管理 / 限流 / IP 限制”彼此割裂，缺少服务治理工作台的整体感。

## 总体目标

### 权限管理目标

将权限管理重构为以下模块：

- 角色管理
- 用户权限
- 客户端权限
- 权限目录
- 菜单与按钮
- API 资源管理

其中：

- “菜单与按钮”是权限资源维护入口。
- “权限目录”是权限资源查看/审计入口。
- “API 资源管理”是接口资源维护入口，不能只做全量目录展示。
- “角色管理 / 用户权限 / 客户端权限”是授权入口。
- “按钮”不再作为独立一级导航入口出现，但旧路由可以保留兼容。

### 网关管理目标

将网关管理重构为以下模块：

- 服务发现
- 路由管理
- 灰度发布
- 限流策略
- IP 黑白名单
- 路由诊断
- 访问日志

其中第一阶段优先完成：

- 服务发现页面
- 路由管理接入 Nacos 服务选择
- 动态路由刷新修复
- 路由运行态状态展示

第二阶段再完成：

- 灰度规则模型
- Gateway 灰度过滤器 / 负载均衡策略
- 灰度发布页面
- 路由诊断增强

## 设计原则

- 菜单是页面入口资源，按钮是页面内操作资源，按钮必须归属于菜单。
- 菜单、按钮、API 都是权限资源，但管理入口应体现它们的业务层级。
- 授权页面面向业务理解，应按“菜单树 -> 按钮”分配，不应让管理员面对平铺的 `ACTION_*` 列表。
- Nacos 是服务注册中心事实来源，路由配置必须优先引用 Nacos 服务。
- DB 仍作为管理台配置来源，用于存储路由、灰度、限流、IP 策略等治理规则。
- Gateway 运行态必须可刷新、可观察、可诊断。
- 灰度规则不要写死在路由 YAML 中，应该由 DB 配置并动态刷新。
- 前端页面不要只做 CRUD，要围绕“服务 -> 路由 -> 策略 -> 发布状态”组织。
- 本阶段尽量不破坏现有接口，优先兼容已有 `gateway_route` 表和页面。

## 权限管理改造方案

### 1. 导航分组调整

文件：

- `jbm-admin-vue/src/constants/adminNav.ts`
- `jbm-admin-vue/src/router/index.ts`

目标导航：

```text
权限管理
  角色管理
  用户权限
  客户端权限
  权限目录
  菜单与按钮
```

调整要求：

- 将“菜单管理”从“其他”移动到“权限管理”。
- 将“菜单管理”改名为“菜单与按钮”。
- 将“按钮管理”从主导航中移除。
- 保留 `/system/actions` 路由兼容旧链接，可重定向到 `/system/menus`，也可保留独立页面但不出现在导航。
- `MENU_PATH_ALIASES` 中增加 `/system/actions -> /system/menus`，避免已有后端菜单路径导致授权后无法访问。
- `menuCodes` 建议包含 `['menus', 'menu', 'actions', 'action']`，确保只有按钮权限但有资源维护需要的角色仍能看到入口。

### 2. 合并菜单与按钮页面

主页面：

- `jbm-admin-vue/src/views/system/MenuList.vue`

现有按钮页：

- `jbm-admin-vue/src/views/system/ActionList.vue`

建议做法：

- 以 `MenuList.vue` 为主，嵌入按钮管理能力。
- `ActionList.vue` 暂时保留，后续可删除或只作为兼容组件。
- 页面名称改为“菜单与按钮”。
- 页面布局建议：
  - 上半区或左侧：菜单列表/菜单树。
  - 右侧或下半区：当前选中菜单的按钮列表。
  - 未选择菜单时，按钮区域显示“请选择菜单”。

最小改造版本：

- 保留现有菜单表格。
- 在每行菜单操作区增加“按钮”按钮。
- 点击后打开抽屉或宽弹窗，管理该菜单下按钮：
  - 列表：按钮编码、按钮名称、权限标识、排序、状态。
  - 新增：默认带入当前 `menuId`，不允许为空。
  - 编辑：不建议修改所属菜单；如允许修改，必须明确展示。
  - 删除：二次确认。

更推荐版本：

- 表格点击选中菜单。
- 页面底部固定显示“当前菜单按钮”区域。
- 这样菜单和按钮的从属关系更直观。

### 3. 按钮管理逻辑约束

前端约束：

- 新增按钮必须有 `menuId`。
- 从“菜单与按钮”进入按钮新增时，`menuId` 自动继承当前菜单。
- 权限标识只展示生成结果：`ACTION_{actionCode}`。
- 不要让用户手动输入 `ACTION_` 前缀。
- 按钮编码建议提示：
  - `users_add`
  - `users_edit`
  - `monitor:online:forceLogout`

后端约束建议：

- `BaseAction.menuId` 必填。
- 新增/更新按钮时同步 `BaseAuthority`。
- 删除按钮时级联删除/清理对应 action 权限授权关系。
- 如果当前后端已做到同步，前端不重复处理。

### 4. 权限目录优化

文件：

- `jbm-admin-vue/src/views/authority/AuthorityCatalog.vue`

目标：

- 权限目录是查看和审计页，不是主要维护页。
- API 权限继续独立展示。
- 菜单和按钮不要完全平铺割裂。

建议改造：

- 将 tab 从：

```text
API 权限 / 菜单权限 / 按钮权限
```

调整为：

```text
API 权限 / 页面权限
```

- “页面权限”内部按菜单展示：
  - 菜单名称
  - 路径
  - `MENU_{menuCode}`
  - 下挂按钮 `ACTION_{actionCode}`
- 也可以保留“按钮权限”筛选，但展示时带上所属菜单名称和路径。

### 5. 角色/用户授权优化

文件：

- `jbm-admin-vue/src/views/system/RoleList.vue`
- `jbm-admin-vue/src/views/authority/UserPermissionList.vue`

当前已经按菜单下挂按钮展示，继续保留。

需要增强：

- 勾选按钮时自动勾选所属菜单。
- 取消菜单时，默认同步取消下属按钮；如果担心误操作，可弹确认。
- 菜单 checkbox 支持半选状态：
  - 部分按钮选中但菜单未完全选中时显示 indeterminate。
- 增加“全选当前菜单按钮 / 清空当前菜单按钮”快捷操作。
- 保存前校验：
  - 如果存在已选按钮但所属菜单未选中，自动补齐菜单权限。

### 6. 系统管理分组清理

当前“其他”分组不合理。建议：

- 审计日志可单独归入“日志审计”。
- 开发者可归入“开放平台”。
- 菜单与按钮归入“权限管理”。
- 如果短期不想大改，至少先移走“菜单管理 / 按钮管理”。

## API 管理改造方案

### 1. 当前问题确认

当前页面：

- `jbm-admin-vue/src/views/api/ApiRegistryList.vue`

当前前端接口：

- `jbm-admin-vue/src/api/authority.ts`
- `listApis(serviceId?)` 调 `/authority/apis`
- `listResources()` 调 `/authority/resources`

当前后端接口：

- `BaseApiController`
- `GET /api` 当前返回 `apiService.findAllList(serviceId)`，没有分页。
- `BaseApiServiceImpl#findListPage(BaseApiForm)` 已有分页查询能力，但 Controller 未暴露为标准分页接口。
- `BaseApiController` 已有创建、更新、删除、批量删除、批量公开状态、批量访问日志、批量状态、批量认证等操作，但前端 API 注册中心页面没有使用。

因此，API 管理的合理方向不是继续增强 `/authority/apis`，而是把 `API 注册中心` 改成真正的 `API 资源管理`，直接对接 `/api` 资源接口。

### 2. 页面定位

建议将当前“API 注册中心”改名为：

- `API 资源管理`

语义：

- 管理 `base_api` 资源。
- 负责接口资源的增删改查、启停、公开/保护、认证要求、访问日志开关。
- 与 API Key 授权、限流策略、IP 策略形成入口联动。

权限目录中的 API tab 仍可保留，但它是“权限视角”的只读审计，不承担资源维护。

### 3. 后端接口设计

优先复用已有 `/api` Controller。

需要调整 `GET /api`：

- 如果带分页参数，返回 `DataPaging<BaseApi>`。
- 如果不带分页参数，可以兼容返回全量列表，但前端管理页必须使用分页模式。

建议接口：

```text
GET /api
```

查询参数：

- `pageForm.currPage`
- `pageForm.pageSize`
- `serviceId`
- `path`
- `apiName`
- `apiCode`
- `status`
- `isAuth`
- `isOpen`
- `accessLog`

返回：

```json
{
  "contents": [],
  "total": 123,
  "pageForm": {
    "currPage": 1,
    "pageSize": 20
  }
}
```

已有操作接口应在前端接入：

```text
GET    /api/{apiId}
POST   /api
PUT    /api/{apiId}
DELETE /api/{apiId}
DELETE /api?ids=1,2,3
PATCH  /api?ids=1,2&open=true
PATCH  /api?ids=1,2&accessLog=false
PATCH  /api?ids=1,2&status=1
PATCH  /api?ids=1,2&auth=1
```

建议补充：

```text
GET /api/services
```

或复用网关服务发现接口，给 API 管理页提供服务筛选。

### 4. 后端查询增强

`BaseApiServiceImpl#findListPage` 建议增强：

- 支持 `isOpen` 查询。
- 支持 `accessLog` 查询。
- 支持 keyword 查询：
  - path
  - apiName
  - apiCode
  - serviceId
- 排序建议：
  - serviceId ASC
  - path ASC
  - createTime DESC 作为兜底。

注意：

- 新增/更新 API 后必须继续同步 `BaseAuthority`。
- 删除 API 时必须继续清理 API 权限及授权关系。
- 批量删除必须不要绕过 `baseAuthorityService.removeAuthority`，否则会留下孤儿权限点。当前 `batchDeleteApis` 直接 `apiService.remove(wrapper)`，建议改为逐个 `apiService.removeApi(apiId)` 或新增 service 批量方法统一清理权限。

### 5. 前端 API 模块设计

新增或调整文件：

- 新增 `jbm-admin-vue/src/api/baseApi.ts`
- 或在现有 `authority.ts` 外单独拆分，避免权限目录和 API 资源管理混在一起。

建议方法：

```ts
export async function listBaseApis(page, size, query)
export async function getBaseApi(apiId)
export async function createBaseApi(data)
export async function updateBaseApi(apiId, data)
export async function deleteBaseApi(apiId)
export async function batchDeleteBaseApis(ids)
export async function batchPatchApiOpen(ids, open)
export async function batchPatchApiAuth(ids, auth)
export async function batchPatchApiStatus(ids, status)
export async function batchPatchApiAccessLog(ids, accessLog)
```

类型建议补齐：

```ts
export interface BaseApi {
  apiId?: number
  apiCode?: string
  apiName?: string
  serviceId?: string
  path?: string
  requestMethod?: string
  apiCategory?: string
  status?: number
  isAuth?: boolean | number
  isOpen?: number
  accessLog?: boolean
  isPersist?: boolean
  priority?: number
  businessScope?: string
}
```

### 6. API 资源管理页面设计

文件：

- `jbm-admin-vue/src/views/api/ApiRegistryList.vue`

建议重构为：

- 页面标题：`API 资源管理`
- 副标题：`维护 base_api 接口资源，控制认证、开放访问、访问日志和授权入口。`

筛选区：

- 服务下拉：来自服务发现或 `/api` 聚合。
- 请求方法：GET / POST / PUT / DELETE / PATCH / ALL。
- 状态：启用 / 停用。
- 访问类型：公开 / 需授权。
- 认证要求：需要认证 / 不需要认证。
- 访问日志：开启 / 关闭。
- 关键词：路径 / 名称 / 编码。

表格列：

- 勾选框
- API ID
- 方法
- 路径
- 名称
- 编码
- 服务
- 访问类型：公开 / 需授权
- 认证：需要 / 不需要
- 访问日志：开 / 关
- 状态
- 操作

行操作：

- 编辑
- 启用 / 停用
- 公开 / 保护
- 开启 / 关闭访问日志
- 关联限流
- 关联 IP 策略
- 查看授权
- 删除

批量操作：

- 批量启用
- 批量停用
- 批量设为公开
- 批量设为需授权
- 批量开启访问日志
- 批量关闭访问日志
- 批量删除

分页：

- 必须使用后端分页。
- 默认 20 或 50 条。
- 不再通过全量拉取做本地分页。

### 7. API 编辑弹窗

字段：

- API 编码 `apiCode`，必填。
- API 名称 `apiName`，必填。
- 服务 ID `serviceId`，必填，建议从服务发现选择。
- 路径 `path`，必填。
- 请求方法 `requestMethod`。
- 分类 `apiCategory`。
- 业务范围 `businessScope`。
- 是否公开 `isOpen`。
- 是否需要认证 `isAuth`。
- 是否记录访问日志 `accessLog`。
- 状态 `status`。
- 排序 `priority`。

约束：

- `apiCode` 不让用户输入 `API_` 前缀。
- 权限标识展示为只读：`API_{apiCode}`。
- `isPersist=true` 的保留接口不允许删除，编辑时也应限制关键字段。

### 8. 与网关治理联动

API 管理页面应提供快捷入口：

- `关联限流`：跳转或打开弹窗，将当前 API 加入 `gateway_rate_limit_api`。
- `关联 IP 策略`：跳转或打开弹窗，将当前 API 加入 `gateway_ip_limit_api`。
- `API Key 授权`：跳转到 API Key / 客户端权限授权页面，并带上当前 API 搜索条件。
- `路由诊断`：根据 `serviceId + path` 检查当前 API 是否能被某条网关路由覆盖。

### 1. 修复动态路由刷新残留

位置：

- `jbm-cluster/jbm-cluster-platform/jbm-cluster-platform-gateway/src/main/java/com/jbm/cluster/platform/gateway/locator/DynamicRouteDefinitionLocator.java`

要求：

- 在重新加载 DB 路由前，清理上一轮动态路由。
- 只清理 DB 动态路由，不误删 YAML 静态路由。
- 维护一个 `Set<String> dynamicRouteIds`，每次加载前先删除这些 ID。
- 删除完成后再加载新的 `gateway_route` 和限流路由。
- 限流路由 ID 建议加固定前缀，例如 `rate-limit-{apiId}`，避免和普通路由 ID 冲突。

建议逻辑：

```java
private final Set<String> dynamicRouteIds = ConcurrentHashMap.newKeySet();

private Mono<Void> clearDynamicRoutes() {
    List<Mono<Void>> deletes = dynamicRouteIds.stream()
            .map(routeId -> repository.delete(Mono.just(routeId)).onErrorResume(e -> Mono.empty()))
            .collect(Collectors.toList());
    dynamicRouteIds.clear();
    return Mono.when(deletes);
}
```

加载新路由成功后：

```java
repository.save(Mono.just(definition)).subscribe();
dynamicRouteIds.add(definition.getId());
```
