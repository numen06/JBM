# JBM 登录、访问与安全审计

纯日志使用现有 JBM 日志服务、Kafka 和 Loki；控制、设备状态、能源计费等业务历史继续按业务规范使用 TDengine。本项不把业务历史搬回 Loki。

## 权限与入口

- 超级管理员在 JBM 安全审计查看全平台记录；授权的只读安全审计角色使用 `ACTION_security.audit.read`。审计角色不能据此修改组织、角色、用户或日志。
- 日志入口统一归入“日志管理”。租户管理员使用“审计日志”查看当前授权范围；超级管理员同时可见“审计日志”和“全局审计”。页面分类为业务操作、登录记录、接口访问，沿用既有权限。服务端依据已验证身份固定租户，拒绝外租户参数和请求头；不能修改或删除记录。该入口不开放整套 JBM 工作区。
- 超管的技术归属租户不是事件的业务归属。服务端已验证的目标用户归属可以记为租户事件；其他全局操作及无法核实归属的历史仅供全局查询。不根据当前用户名映射臆造历史租户。
- `/logs/securityAudit/query` 只接受结构化筛选，不向浏览器开放 Loki 凭据和任意 LogQL。默认最近 24 小时，单次最大 31 天；较大结果须按时间或账号分段查询。

## 可靠投递与留存

认证服务记录登录结果；网关从受信任的后端响应取得操作者和业务结果，不信任客户端伪造的审计身份。凭据与会话头脱敏。

MySQL `security_audit_outbox` 仅保存待投递事实，经 Kafka 发送给现有 logs 服务。日志服务先持久写入独立备份卷并校验 HMAC，再写 Loki，逐条回读一致后按事件编号及原正文比较删除 outbox。失败保留重试；重复消息不覆盖旧事实。不要把数据库收到消息或 HTTP 200 当归档成功。

配置日志保留 365 天，覆盖网络日志至少六个自然月的要求；业务历史三年的要求另按 TD 规范执行。Loki 实际后端保留期、所有数据目录及 WAL 均必须位于持久卷，独立审计备份卷也必须持久化。日志查询成功不代替持久性验收。

`jbm.logs.security-audit.integrity-key` 至少 32 字节，只通过服务端秘密配置注入；轮换时保留旧 `verification-keys`，不能使历史记录失去验证能力。备份不接入在线业务查询。管理员没有日志删除接口；Loki 删除端点须由反向代理封禁。

## 上线步骤

1. 遵循主线版本 SOP，构建同一个冻结提交的 center、auth、gateway、logs、web/packages；宿主更新共享管理包和 web。先在原本地 debug 服务验收。
2. 保留运行配置、数据库和数据卷。先备份当前认证关联表与 Loki，核对后端路径是否真的落盘；迁移持久路径须停写冷备、逐文件比较哈希后启动，不重建空卷覆盖原数据。
3. 使用候选 center 镜像运行 Alembic 升级。新表保存密码年龄元信息、最新登录状态、未确认安全告警和短期 outbox，不修改既有密码、成员授权或密钥。
4. 准备日志服务独立可写备份卷，以 logs 的有效 UID/GID 管理；注入私有完整性密钥，启用 `jbm.security-audit.enabled`，配置 logs Loki 连接与实际后端一年留存。先验证日志服务写入及回读，再更新生产者。
5. `python -m jbm_cluster_py.platform.logs.archive_legacy` 先归档旧 `base_account_logs` 和 `gateway_logs`。保存脱敏在线事实、私有原记录备份及校验结果。重复运行必须得到相同事实。
6. 通过归档和回读核验后，使用同一命令加 `--delete-verified` 比较原记录并逐条清理 SQL 历史。禁止 TRUNCATE。归档失败、记录变化或备份校验失败必须保留原数据。SQL 清理后再次验收登录、日期查询、安全告警、访问与管理日志；不能依赖 SQL 历史 fallback。
7. 用正式文件密钥登录，执行 JBM 发布契约；最终截图以 `jxdx_admin` 租户管理员为主，含本租户登录/操作、跨租户拒绝、只读限制；超管全局查询单独补充。保留源码 SHA、镜像摘要、检查结果、截图哈希与环境信息。

## 历史归档补充规则

- 批量备份可并行执行 fsync，但每个原记录备份和签名备份仍须逐条读回。SQL 清理在同一个事务中一次锁定本批原记录，逐条比较完整正文后再批量删除，不能省略比较。大表迁移前检查时间及主键的组合索引，避免每批全表排序；临时索引在归档对账后移除。
- 原登录时间为空但原创建时间有效时，保留登录时间为空，按原创建时间以 `legacy-record` 分类归档，不计作已知时间的登录事件；两个时间都缺失时保留 SQL 并报错。分页排序和游标须使用同一个时间表达式。
- 导入超过默认留存期限的旧记录前，先核对最早时间，配置独立旧来源的保留策略及允许导入时间，不能伪造为导入时刻。云端本次 `legacy-login` 和 `legacy-gateway` 来源设置三年，新增审计仍为一年；原始字段和未带时区的原始时间文本保留在备份及历史事实中。
- 接入网关在业务响应完成后执行访问审计持久化，框架在优雅关闭时等待这些任务。日志写入故障须输出错误诊断，不能把已执行成功的业务响应改成 502，诱导用户重复下发。

## 业务操作闭环

- 业务操作列表使用原 securityAudit 事件，按 operationId 在服务端汇总后分页，原签名事实保留于详情。汇总元信息与签名代表事件分开；多任务未全部完成不能显示成功。汇总仅支持完整查询范围内最多 4900 条原事件，超出须缩小时间、人员或模块；不能合并一页样本后冒充完整总数。
- 审计查询本身属于重要管理行为，成功和失败均经统一中间件留痕。已有纯请求采集继续保留；业务操作视图不替代原始访问记录。查询仍使用结构化筛选与服务端范围校验。
- 合法用户编号 0 与未认证身份分别处理；业务审计与访问采集保留原编号，不修改账号或租户授权。
- Loki 查询只解析实际筛选字段，计数时移除无关动态标签；统计使用 countOnly 直接精确计数，并行计算今日与 30 天窗口，不读取无关详情。时间窗口按事件的毫秒精度统一边界；普通分页和详情仍逐条验证签名，操作汇总仍在完整范围核验后分页。性能验收使用相同固定时间区间比较总数、首页事件编号及签名，保留冷查询、慢样本和失败记录。

- 公共资源服务在已验证身份之后记录业务操作。操作前持久写入 START，业务返回时记录 RESULT；排队任务记录 ACCEPTED，不把受理当成功。失败、未确认与设备写入应答分别显示，查看详情可沿同一个 operationId 追查提交内容、目标、业务编号及最终结果。
- 审计暂存目录 `/app/data/security-audit-spool` 必须挂持久卷；开启审计但使用容器临时层会拒绝启动。凭据、密钥、令牌和验证码不进入提交内容。操作开始无法可靠记录时不执行操作；已执行的操作不因归档故障伪装成业务失败。
- 来源端通过现有 Kafka 投递；日志服务先完成独立签名备份与 Loki 精确回读，再通过 Redis 提供摘要匹配的归档确认。来源文件只有核对这一确认后才删除；Kafka ACK 本身不够。Redis 仅保存确认和投递健康状态，不保存唯一日志历史。
- 日志健康同时检查来源端未确认文件、最早积压和心跳。超过 30 秒的归档积压或来源状态失联不能显示正常。租户只获得自己范围的积压信息，不获得其他租户的记录或数量。
- 数据库异步运维任务将 operationId 与原操作者保存在任务关联中，完成后记录结果；重启后补投未确认的完成事件。设备控制通过独立历史工作进程，在 TDengine 业务历史回读一致之后投递纯审计摘要，不在控制调度线程中执行日志网络或磁盘 I/O，也不重发设备指令。

## 接入限制及兼容性

`jbm.admin-access.mode` 升级保留现有设置（默认 `monitor`），内置回环、RFC1918 局域网及 IPv6 ULA 范围。超级管理员在“IP 限制→管理员接入限制”配置网段并启停限制，配置由现有 Nacos 长轮询同步。启用前校验当前管理地址获准；空范围、无效网段及覆盖全部的 /0 不允许保存；并发修改按版本校验，防止误覆盖。来源从可信代理链右向左核实，客户端不能伪造管理网段。内部 userinfo 只验证凭据，资源服务校验真实管理来源。

密码生命周期按配置启用，现有密码首次核实时建立年龄基线，不立即修改密码或批量锁号。旧 `mustChangePassword` 提醒保留原行为，只有新的已验证 `passwordExpired` 才限制业务操作并保留改密通道。必须回归密码、文件密钥、刷新、租户身份和现有成员权限。

## 验收范围

本专项证明 JBM 管理登录、日志审计、租户隔离及相关持久性。不能据此宣称整个等保对象已通过二级测评；管理员允许网段、外围网络/主机控制、异地备份及管理制度等需要各自的实际证据。


## 部署时的业务审计接入检查

- JBM 八个后端角色、建筑 API／批处理及 IoT API／控制历史／飞鸽运维工作进程均须接入。独立鉴权中间件也必须在验证身份后执行统一审计。后台审计启动失败时工作进程不得继续报告正常启动。
- 通过只读密钥文件 `JBM_OPERATION_AUDIT_CONFIG_FILE` 显式注入审计 Kafka、Redis 和 Nacos 连接；此配置仅用于审计，保留宿主原业务配置。宿主采用同一冻结 JBM 制品中的公共审计及认证 Nacos 客户端，不能漏带认证适配器。
- 多个 Docker 网络中可能存在同名 `kafka`／`redis`。审计端点必须明确指向日志服务使用的实例；Kafka 的 advertised listener 也须在全部客户端网络中无歧义，不能仅修改 bootstrap 地址。保留原认证、数据卷和业务控制 Kafka。
- 来源暂存卷必须持久挂载，并保留应用用户权限。日志签名备份为独立持久卷；来源只在日志服务完成签名备份、Loki 精确回读并返回相同摘要的确认之后清理。
- 验收必须核对实际部署角色的投递心跳、积压及扫描错误，不能只看容器健康。完整集成环境本次包括八个 JBM 来源、两个建筑来源及三个 IoT 来源。再用租户管理员进行真实修改并恢复、验证拒绝操作、异步任务最终结果及跨租户拒绝，留存只读查询和截图证据。
- 写入应答和最终状态分开；按产品声明仅需 write_ack 的动作，以设备应答作为该动作的完成标准。timeout／unknown 不可因 HTTP 200 而显示成功，迟到回执继续追加。详情超过查询范围时明确提示记录不完整，不推断整组成功。
