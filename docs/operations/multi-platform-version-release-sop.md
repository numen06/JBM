# 三平台主线与镜像版本发布标准

适用于建筑平台、IoT、JBM 的正常发布、紧急修复、仅前端更新、后端修复和回滚。三个平台独立管理版本；一次发布先确定平台、主线、版本号和服务清单，再构建和上线。紧急发布同样遵守本标准。

本标准替代旧 SOP 中按任意功能名、无主线约束的日期快照、环境或临时分支命名正式镜像的做法。现有镜像与 Git 标签保留为历史记录，不重新打标伪装成统一版本。本次文件整理没有修改线上服务，也没有执行主线改名。

## 1. 平台与主线

| 工作区与平台 | 仓库 | 当前有效 Git 主线 | 统一后的 Git 主线 | 正式镜像版本系列 |
| --- | --- | --- | --- | --- |
| 系统，JBM | JBM7 | `7.3-python` | `py-7.3` | `py-7.3-YYYYMMDD.N` |
| 物联，IoT | iot-platform-jbm | `jbm` | `py-2.0` | `py-2.0-YYYYMMDD.N` |
| 建筑，建筑平台 | smart-building-platform-py | `py` | `py-2.0` | `py-2.0-YYYYMMDD.N` |

`YYYYMMDD` 为 Asia/Shanghai 日期，`N` 为本平台当天独立递增的正整数。IoT 与建筑处于不同仓库，`py-2.0` 同名不表示两个平台共用版本计数器。平台身份必须同时包含仓库，不能只靠分支名或 tag 判断。

主线同名迁移方案已确定，尚未执行。新格式正式发版前必须完成主线同名迁移并同步仓库规则、钩子和流水线。当前主线仍保留用于开发和验证，不得在旧名主线上出一个前缀不匹配的新格式正式包；也不能凭目标名称创建一个来源不明的新主线。旧 `dev`、`master`、Java 版本及其他历史正式分支保持独立，不自动合并为 Python 主线。

## 2. 镜像出包规则

1. 正式格式固定为 `<Git主线>-YYYYMMDD.N`。JBM 为 `py-7.3-YYYYMMDD.N`；IoT 与建筑分别为 `py-2.0-YYYYMMDD.N`。主线部分必须与该平台 Git 主线逐字一致，不按环境、服务或功能另外命名。
2. `YYYYMMDD` 使用 Asia/Shanghai 的发布日期；`N` 是该平台、该主线、当天独立递增的正整数，从 1 开始。跨平台不共享序号。普通更新、紧急修复、仅改前端或单个接口均占用下一序号。新的一天重新从该日已占用最大序号加一，不能只看正在运行的旧版本。
3. 示例：`py-7.3-20261102.1` → `.2`；次日可为 `py-7.3-20261103.1`。IoT 与建筑都可各自拥有 `py-2.0-20261102.1`，必须通过镜像仓库名区分平台。这些是命名示例，不表示已预留或已经发布。
4. 分配前核对远端 Git 标签、镜像仓库和发布台账。同平台、同主线、同日期取所有已占用序号的最大值再加一。失败、取消或未上线的构建也占号；不复用、不覆盖、不把旧 tag 移到新 commit。冻结后即使构建跨越零点，也沿用已预留的完整版本号。
5. 每个仓库维护一份 `VERSION` 保存本次完整版本，例如 `py-7.3-20261102.2`；全部发布配置由它生成或校验一致。同一平台本次输出的 Web、API、Worker 和基础服务镜像共用完整 tag，组件由镜像仓库名区分。
6. 功能名和时间详情放更新记录。完整版本写入 `org.opencontainers.image.version`，完整源码提交写入 `org.opencontainers.image.revision`；两个身份分别记录。Git 发布 tag 使用同一完整版本号，并固定到经过验证的主线提交。
7. 同一个版本的不同组件允许 digest 不同；同一镜像仓库的同一个 tag 只能对应一次构建结果。部署使用 `image:version@sha256:digest`。构建一次后以同一摘要跨环境晋级，不在不同环境重建同名 tag。
8. 环境差异通过配置、密钥和挂载表达；确有不同制品时在组件名或变体清单中说明。环境名、功能名、commit 不能替代上述正式版本格式。
9. 本地、候选、部署中、已上线、失败、已回滚是状态，不是另一套版本号。验收与实际运行核对完成后才登记成功。

历史 `py-7.3.48`、`py-2.1.<日期>.<序号>`、`cloud-*` 和功能快照保留原样用于追溯。新规则不按它们的字符串大小或补丁数字换算当天序号；首次启用某一日期前仍须查询现有同格式标签，避免重复占号。不能把旧混合镜像重新改标后宣称完成统一升级。

配置文件顶层 `version: "1.0"` 是 App2Docker 配置结构版本，不是产品出包版本；正式镜像版本在 `VERSION` 和 `image.tag` 中管理。

## 3. 开发分支与合回

允许从本平台当前有效主线创建短期 `feat/<事项>`、`fix/<事项>`、`hotfix/<事项>` 分支。分支只用于开发、评审和验证，不能成为独立正式发布源码。

标准顺序为：**从主线开发 → 分支验证 → 评审并合回主线 → 冻结主线提交 → 分配新版本 → 构建 → 验收 → 上线 → 记录**。主线保持可发布，未完成的功能留在开发分支或以已验证的功能开关隔离。

紧急修复可用生产版本定位问题，但最终修复必须回到主线，正式镜像仍从包含修复的主线提交构建。不得从热修复分支、脏工作区、本地复制目录、旧发行仓库或历史 Java 分支直接出正式包。

合回后确认代码和配置均包含本次修改；不能用“提交存在”代替文件与功能核对。删除开发分支前保存历史与未提交文件，并确认已合并或经逐项验证等价包含。未合并业务代码和正在使用的工作树必须单列处理，不能批量强制合并、删除或偏向某一侧解决冲突。

## 4. 发布配置只保留明确入口

每个仓库以 `deploy/release-catalog.json` 列出当前保留入口、用途和版本系列；原 App2Docker 继续作为构建系统。新增功能不能再复制一份带功能名、日期的新发布 profile 或 Dockerfile。

- 共用构建逻辑合到通用 Dockerfile，以服务 target 和明确参数区分组件。
- 镜像 tag 必须来自本次统一版本；只改变发布类型和环境不能另开版本体系。
- `.app2docker.yaml` 是现有全量配置模板，默认推送已禁用，防止旧流水线重用历史标签；启用正式推送前须完成标准化版本与服务目标迁移。必须核实每个服务实际选择了正确 stage。服务名相同、构建完成或健康检查通过，都不能代替镜像内容验证。
- 当前仍需保留的少数专项配置标为兼容入口；其已有 tag 仅记录历史。下一次正式使用前必须显式传入本标准的新版本，并完成版本元数据及内容校验，不能继续使用功能名 tag。
- `deploy/release-archive/20261102/` 保存已退出当前入口的一次性配置与 Dockerfile；内容、原路径、来源 commit、SHA-256 和保留原因有索引。归档文件不可直接作为正式发布入口。
- `docs/releases/` 保存不可改写的历史验收记录。历史记录中的路径按当时 commit 解释，不为了目录变动重写历史证据。

本轮先收敛历史入口；`VERSION`、版本分配、标准化参数生成与流水线迁移属于下述落地项，不能把文件归档理解成运行镜像已统一。

## 5. 正常发布流程

1. **确认范围**：确定平台、环境、变更、全部计划服务及依赖，记录当前三平台实际版本组合和回滚基线。
2. **冻结源码**：修复合回主线；工作区干净且已经推送。保存完整 commit。Git 发布 tag、构建任务读取的源码和主线冻结提交必须一致。
3. **预留版本**：核对已占用编号，更新 `VERSION`、发布清单和构建配置，确保所有输出镜像共用新版本。标签一旦预留不得移到另一个 commit。
4. **本地验证**：完成必要测试与构建，更新原本实际运行的本地服务，再从原 debug 地址实操。另起预览服务或只生成 `dist` 不算本地已更新。
5. **App2Docker 构建**：使用原流水线、Git 源及冻结的主线提交，显式设置版本与服务范围。不通过其他 Git 仓库、临时源码副本或本机直接 Buildx 绕过正式流程。
6. **制品核对**：核对任务的 branch/ref、实际 commit、profile、每个镜像 tag 和 AMD64/ARM64 清单。隔离验证入口、依赖和关键文件，确保没有把 Web stage 当后端镜像；核对 OCI version/revision、迁移与运行扩展。
7. **准备回滚**：保存旧服务规格、镜像摘要、配置和数据迁移 revision。对将触及的数据按现有授权和备份流程备份并校验；不要为普通镜像发版自动恢复或清空数据库。
8. **分批部署**：仅更新本次相关平台与计划服务，保留既有环境变量、密钥、网络、卷、副本及消费语义。需要依赖升级时通常按 JBM → IoT → 建筑推进，每一步稳定后再继续。
9. **完整验收**：检查服务、页面和实际业务接口。HTTP 200 仍须业务成功；功能性 404、403、500、错误跳转和操作卡住都算失败。JBM 运行只读接口契约及菜单验收；IoT 核对采集、控制回执和路灯数据完整性；建筑核对项目空间、API、批处理、报表与数据新鲜度。
10. **核对运行版本**：每个计划服务的实际 image、版本、revision 和 digest 必须与清单一致。仅一部分服务已切换时标记“部署中／部分完成”，不能宣布整套平台已统一。
11. **登记结果**：保存最终环境组合、构建任务、镜像和测试结果。完成后再关闭发布事项和清理已合并开发分支。

现场控制验收必须已有用户授权和恢复措施；默认使用只读真实状态，不自动下发控制或伪造遥测。数据库运维的验收不自动提交备份、还原或启用策略。

## 6. 紧急修复和局部上线

紧急时可以缩小受影响服务和测试范围，但不能跳过主线合回、版本递增、Git 源构建、镜像内容校验、回滚基线及修复项实际验收。先保存故障日志与请求编号，发布记录写清缩小了哪些验证和后续补验责任。

只更新一个服务也使用本平台下一个版本，其他服务的真实版本继续如实登记。若此次目标是整套版本统一，必须在同一冻结 commit 下补齐剩余计划制品并完成核对后才收敛为整套发布；不能靠改标签或服务显示版本掩盖旧内容。冻结后的源码若再修改，则另增版本，不覆盖已发布制品。

禁止 SSH 直接改容器里的代码作为正式修复；禁止不符合主线日期格式的功能专用版本号、覆盖旧 tag、手工上传未追踪源码、从热修分支独立发版，或在生产临时关鉴权、换数据库、绕过验证码来完成验收。

## 7. 回滚规则

回滚使用上一个已验收清单中的原镜像摘要和兼容配置，不重建、覆盖旧版本，也不把旧内容改标成新版本。回滚操作单独记事件，实际运行版本明确显示退回的旧版本；下一次修复按对应主线和发布日期，从该日所有已占用序号的最大值继续递增。

应用回滚与数据回滚分开判断。向后兼容的表和索引通常保留，不能为了应用回滚自动删数据；数据库恢复可能覆盖新增业务数据，必须单独评估并取得相应授权。回滚后复核认证、消息、设备连接及数据新鲜度，并保留失败版本和原因。

## 8. 一份发布清单必须包含的字段

| 类别 | 必填内容 |
| --- | --- |
| 平台 | 平台标识、仓库、当前有效主线、正式版本号、发布类型与状态 |
| 源码 | 完整 commit、Git tag、合回记录、工作区与远端核对结果 |
| 构建 | App2Docker 任务、profile、Dockerfile、实际 stage、架构、基础镜像摘要 |
| 制品 | 每个组件的镜像名、统一 tag、OCI version/revision、digest、内容验证结果 |
| 环境 | 目标域名与集群、部署前后服务规格、三平台实际版本组合 |
| 数据 | 迁移 revision、配置差异、必要备份位置和校验值，不记录秘密 |
| 验收 | 自动测试、本地原服务验证、线上菜单/API、关键业务和数据核对 |
| 回滚 | 旧版本和 digest、兼容条件、触发条件、执行及恢复结果 |

提交号、镜像号和数据版本分别记录。SDK、组件包可以有自己的包版本，但它们的精确版本与校验值必须列入制品依赖，不能用包版本替代平台发布版本。

## 9. 主线同名迁移步骤

1. 保存当前正式主线的完整 SHA、远端 refs、工作树和未提交文件。列出仍在工作的会话和流水线，冻结主线切换窗口。
2. 分别以 `7.3-python`、`jbm`、`py` 的已验证最新主线提交作为目标 `py-7.3`、`py-2.0`、`py-2.0` 的唯一基线；确认目标同名分支是否已存在，存在且指向不同则停止核对，不能覆盖。
3. 更新远端默认分支、开发 upstream、分支保护、Git 钩子、主线检查、App2Docker Git 来源和触发规则、文档与发布目录；逐项验证后再启用新的发布入口。
4. 比对迁移前后 tree 和关键代码，确保改名没有改变业务内容。旧正式分支暂留只读追溯，不自动覆盖或批量合并旧版本。
5. 从新主线执行一次只构建和版本检查，再安排正式制品的本地及线上验收。命名统一不等于已经完成软件升级。

- 对旧临时分支按“已合入、仍有独立变更、工作树占用”登记。只清理已验证安全的分支，其余不以强制合并代替源码核对。
