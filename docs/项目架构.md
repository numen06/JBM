## 三、核心逻辑梳理

### 3.1 整体架构分层

JBM7 采用**四层架构**，自底向上为：

```
┌─────────────────────────────────────────────────┐
│              jbm-cluster (集群平台层)              │  ← 业务微服务
│  center / auth / gateway / logs / push / job ... │
├─────────────────────────────────────────────────┤
│              jbm-framework (框架层)               │  ← 技术能力
│  core / data / autoconfigure / micro / web ...   │
├─────────────────────────────────────────────────┤
│              jbm-util (工具层)                    │  ← 基础能力
│  集合 / IO / 加密 / 模板 / 并发 ...               │
├─────────────────────────────────────────────────┤
│         jbm-framework-dependencies (BOM)         │  ← 版本管控
└─────────────────────────────────────────────────┘
```

### 3.2 模块依赖关系

```
jbm-cluster
  ├── 继承 jbm-framework-dependencies (版本控制)
  ├── 依赖 jbm-cluster-api (实体 + Feign客户端)
  ├── 依赖 jbm-cluster-common-* (认证/安全/Feign配置)
  └── 依赖 jbm-framework-* (框架能力)

jbm-framework
  ├── 继承 jbm-framework-dependencies (版本控制)
  ├── jbm-framework-core (不依赖任何JBM模块，最底层)
  ├── jbm-framework-spring / web (依赖 core)
  ├── jbm-framework-data (依赖 core + mybatis-plus)
  └── jbm-framework-autoconfigure-* (依赖对应的第三方库)

jbm-util
  └── 继承 jbm-framework-dependencies (仅依赖版本号，零JBM内部依赖)
```

### 3.3 核心流程

#### 流程一：请求认证链路

```
客户端请求
  → Gateway (端口6060)
    → SaAuthFilter: Sa-Token认证检查
    → ValidateCodeFilter: 验证码校验
    → XssFilter: XSS防护
    → AccessLogFilter: 访问日志记录
    → ApiFilter: API签名验证
    → DynamicRouteDefinitionLocator: 动态路由(从数据库加载)
    → 转发到目标微服务
      → SaServletSuperFilter: 服务端二次鉴权
      → @RequiresPermissions: 方法级权限校验
      → 业务Controller → Business → Service → Mapper → DB
```

#### 流程二：MasterData 代码自动生成（核心亮点）

```
启动类添加 @EnableCodeAutoGeneate 注解
  → AutoScanCodePackages.CodeRegistrar 注册为 ImportBeanDefinitionRegistrar
  → 扫描指定包下的 Entity 类
  → GenerateHelper.scanGnerate() 触发代码生成
    → GenerateMapperCode: 生成 Mapper 接口
    → GenerateMapperXmlCode: 生成 MyBatis XML
    → GenerateServiceCode: 生成 Service 接口
    → GenerateServiceImplCode: 生成 Service 实现
    → GenerateBusinessCode: 生成 Business 接口
    → GenerateBusinessImplCode: 生成 Business 实现
    → GenerateControllerCode: 生成 Controller (自带增删改查REST API)
  → 所有生成的类自动注册为 Spring Bean
  → 无需手写任何 CRUD 代码，直接拥有完整 REST API
```

#### 流程三：集群事件总线

```
服务A发布事件 (@JbmClusterEvent)
  → JbmClusterBusinessEventTemplate 发布 Spring Cloud Bus 事件
  → Nacos / RabbitMQ 传输事件
  → 服务B接收事件
  → StreamAccessLogService / JbmBusinessLogTemplate 处理事件
```

#### 流程四：认证授权流程

```
1. 用户登录 → POST /login → Auth服务(端口5555)
2. Auth服务验证账号密码 → 生成 Sa-Token JWT
3. 返回 Token 给客户端
4. 客户端携带 Token (Header: Authorization: Bearer xxx)
5. Gateway 的 SaAuthFilter 校验 Token
6. 转发到业务服务，SaServletSuperFilter 提取用户信息
7. @RequiresPermissions 注解进行细粒度权限校验
8. SecurityUtils 获取当前登录用户信息
```

> RBAC 数据模型与多应用菜单隔离详见 [应用-菜单-权限关系梳理](应用-菜单-权限关系梳理.md)。

## 四、上下文注释（关键设计决策说明）

### 4.1 为什么要自己包装 `ApplicationEvent`？

JBM在 `jbm-framework-core` 中重新定义了Spring的 `ApplicationEvent`（路径: `org.springframework.context.ApplicationEvent`）。这是因为框架需要在Spring标准事件机制上扩展**集群级别的事件传播能力**。通过重写这个类，可以让所有事件自动支持通过Spring Cloud Bus在微服务之间传播，而不需要每个事件单独配置序列化逻辑。

### 4.2 `ResultBean` vs `ResultBody` 两套返回值封装

项目中存在两个返回值封装类：`ResultBean`（旧版，在framework-core中）和 `ResultBody`（新版）。`ResultBean` 使用 `key + flag + messages + result` 的结构，`flag` 用整数表示状态。新版 `ResultBody` 更现代化，使用链式调用（`.code().msg().httpStatus()`）。新代码应使用 `ResultBody`，`ResultBean` 保留是为了向后兼容。

### 4.3 `MasterDataEntity` 的字段设计意图

`MasterDataEntity` 除了常规的 `id`、`createTime`、`updateTime` 外，还内置了 `code`（业务编码）、`appId`（多租户/多应用隔离）、`parentId`/`level`/`leafPath`（树状结构支持）。这是为了**一个基类同时支持扁平数据和树形数据**的场景，避免每个实体单独处理树形逻辑。`leafPath` 存储从根到当前节点的路径（如 `1/5/12`），用于快速查询子树。`extendData` / `extendQuery` 用于动态字段（`extend_data` JSON 列 + Redis 字段定义），使用方式见 [动态字段使用方案](动态字段使用方案.md)。

### 4.4 Auth 服务排除 `DataSourceAutoConfiguration`

Auth 服务启动时显式排除了 `DataSourceAutoConfiguration`（`@SpringBootApplication(exclude = {DataSourceAutoConfiguration.class})`），因为认证服务本身不直接操作数据库，用户认证信息通过Feign调用Center服务获取。这种设计实现了**认证与业务数据的物理隔离**。

### 4.5 Gateway 使用 WebFlux 而非 Servlet

`JbmGatewayApplication` 使用 `@EnableWebFlux`，因为 Spring Cloud Gateway 基于 Netty + WebFlux 实现，不能使用传统的 Servlet API。网关中的过滤器（如 `SaAuthFilter`）使用的是 `SaReactorFilter`（响应式版本），而非 Servlet 版本的 `SaServletFilter`。

### 4.6 `BaseBusiness.executeInTransaction` 的设计

`BaseBusiness` 提供了 `executeInTransaction` 方法，看起来只是简单地包装了 `@Transactional`。之所以需要这个方法，是因为**Spring事务代理在同一个类中自调用时会失效**（AOP代理的固有限制）。通过将事务操作提取到这个 protected 方法中，子类编排写操作时可以正确触发事务代理，避免数据不一致。

### 4.7 `IBo` 接口设计（业务对象模式）

`IBo<P extends IBizParam, A extends IBizAction>` 定义了 BO（Business Object）模式，包含序列号 `sn`、参数 `param`、动作 `action`。这是一种**命令模式**的实现，将业务操作的"参数"和"动作"分离。适用于工作流、规则引擎等需要将业务逻辑序列化/持久化的场景（如 `jbm-cluster-platform-job` 中的任务调度）。

### 4.8 40+ autoconfigure 模块的意义

`jbm-framework-autoconfigure` 下有40多个子模块，每个模块对应一个技术组件的自动配置。这种"一个组件一个模块"的细粒度设计，使得使用者可以**按需引入依赖**，不会因为引入一个功能而带入大量无关的第三方库。每个模块通过 `spring.factories` 注册自动配置类，Spring Boot 启动时自动加载。

### 4.9 BO 模式的分层架构

框架采用经典的分层调用链：`SuperMapper` → `IBaseSqlService` → `IMasterDataService` → `IMasterDataTreeService` → `BaseBusiness`。每一层都有明确的职责边界：Mapper负责SQL，Service负责数据操作编排，TreeService处理树形关系，Business处理事务和业务逻辑。代码自动生成器会为每个Entity生成完整的调用链。

## 六、新开发者/新AI上手指引

### 快速理解项目的关键路径

1. **先看 `jbm-framework-dependencies/pom.xml`** — 理解整个项目的技术栈和版本
2. **再看 `jbm-framework-data/jbm-framework-data-masterdata/`** — 理解MasterData ORM体系（这是框架的核心价值）
3. **然后看 `jbm-cluster/jbm-cluster-api/jbm-cluster-api-basic/`** — 理解业务实体模型（71个实体类）
4. **接着看 `jbm-cluster/jbm-cluster-platform/jbm-cluster-platform-center/`** — 理解核心业务逻辑（34个Controller）
5. **最后看 `jbm-cluster/jbm-cluster-platform/jbm-cluster-platform-gateway/`** — 理解请求链路

### 开发新微服务的步骤

1. 创建新模块，继承 `jbm-cluster-node-mysql`（MySQL节点模板）
2. 定义Entity类，继承 `MasterDataEntity`
3. 在启动类添加 `@EnableCodeAutoGeneate` 注解
4. 启动后自动拥有完整CRUD REST API
5. 添加 `bootstrap.yml` 配置Nacos连接
6. 在Gateway中配置路由（动态从数据库加载）

### 关键约定

- 所有实体类放在 `jbm-cluster-api-basic` 的 `entitys` 包下
- Feign客户端放在 `jbm-cluster-api-basic` 的 `service/feign` 包下
- 业务逻辑放在对应 platform 模块的 `business` 包下
- Controller 继承 `IMasterDataController` 即可获得标准REST接口
- 新的自动配置模块必须提供 `META-INF/spring.factories`
