# JBM 登录接入指南

本文面向需要接入 JBM 认证中心的下游应用，说明多应用登录、Token 获取、菜单加载和服务间调用的推荐接入方式。

## 一、接入模型

| 接入方 | 推荐方式 | 是否使用 `client_secret` | 说明 |
| --- | --- | --- | --- |
| JBM 第一方前端应用 | 统一登录页 + 授权码闭环 | 否 | 用户在一个登录页选择应用并登录，前端用 code 换 token 后按应用加载菜单 |
| 外部 Web / SPA 应用 | Authorization Code + PKCE | 否 | 浏览器端只能持有公开 `client_id`，不能持有密钥 |
| 外部服务端应用 | Authorization Code + 服务端换 token | 是 | `client_secret` 只保存在服务端 |
| 后端任务 / 服务间调用 | Client Credentials | 是 | 用于服务身份，不代表用户登录态 |

关键原则：

- `client_id` 是公开客户端标识，可以出现在页面、URL 和移动端。
- `client_secret` 是服务端密钥，不能出现在浏览器、前端包、localStorage、URL、日志里。
- 用户菜单和权限以 token 中的 `app_id/client_id/user_id` 为准，由后端接口返回，前端不能自行拼权限。
- `base_app.api_key` 是内部表字段，对外文档统一称为 `client_id`。

## 二、接入前准备

在 JBM 管理端创建应用，得到以下信息：

| 字段 | 用途 |
| --- | --- |
| 应用名称 | 登录页和管理端展示 |
| `client_id` | 登录、授权和菜单隔离使用 |
| `client_secret` | 仅服务端应用或 client credentials 使用 |
| 应用类型 | `pc`、`mobile`、服务应用等 |
| 回调地址 | 授权码模式使用，必须精确匹配 |
| scope | 授权范围，默认可使用 `all` |

应用创建或重置时可以一次性展示 `client_secret`。之后不要提供“明文查看密钥”，只允许重置。

## 三、第一方前端应用登录

适用于 JBM 管理端、TPM、IoT 大屏等属于同一平台的一组应用。用户体验上是一个登录页，不需要明显跳转到授权页。

### 3.1 页面职责

登录页只做三件事：

1. 获取可登录应用列表。
2. 让用户选择要登录的应用。
3. 使用所选应用的 `client_id` 发起授权码登录。
4. 用一次性 `code` 换取 token。

页面不得展示或保存 `client_secret`。

### 3.2 获取应用列表

统一入口部署时：

```http
GET /auth-center/oauth2/apps
Accept: application/json
```

返回示例：

```json
{
  "code": 200,
  "success": true,
  "result": [
    {
      "appId": 1000,
      "appName": "JBM管理系统",
      "code": "jbm",
      "clientId": "jbmSeedDevAppKey00000001",
      "appType": "pc",
      "status": 1
    }
  ]
}
```

前端下拉只展示 `appName/code`，内部保存所选 `clientId`。

### 3.3 用户登录并获取授权码

统一入口部署时：

```http
POST /auth-center/oauth2/doLogin
Content-Type: application/x-www-form-urlencoded

response_type=code&
client_id={client_id}&
redirect_uri={redirect_uri}&
state={random_state}&
username={username}&
password={password_or_rsa_ciphertext}&
scope=all&
loginType=PASSWORD&
vcode={captcha}
```

如果密码已用应用公钥加密，增加请求头：

```http
X-Password-Encrypted: true
```

`loginType` 可以是：

| `loginType` | 页面方式 | `username` | `password` |
| --- | --- | --- | --- |
| `PASSWORD` | 密码 | 用户名 | 密码或 RSA 密文 |
| `SMS` | 短信 | 手机号 | 短信验证码 |
| `FACE` | 人脸 | 手机号 | 人脸图片 Base64 |
| `WECHAT` | 微信 | OpenID | 微信授权 code |
| `MINIAPP` | 小程序 | 手机号 | 小程序登录 code |

响应示例：

```json
{
  "code": 200,
  "success": true,
  "result": "https://app.example.com/login/callback?code=abc&state=xyz"
}
```

前端必须校验返回 `state` 与本地发起值一致，然后再换 token。

### 3.4 用授权码换 token

```http
POST /v3/api/auth/oauth2/token
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code&
client_id={client_id}&
redirect_uri={redirect_uri}&
code={code}
```

响应示例：

```json
{
  "code": 200,
  "success": true,
  "result": {
    "access_token": "eyJhbGciOiJSUzI1NiIs...",
    "refresh_token": "r_xxx",
    "token_type": "Bearer",
    "expires_in": 7200,
    "login_id": "normal:1000:2057849052900044802",
    "user_id": 2057849052900044802,
    "roles": ["admin"],
    "permissions": ["MENU_dashboard"]
  }
}
```

注意：

- 浏览器请求不传 `client_secret`。
- 同一用户选择不同应用登录，会得到不同 `app_id` 和不同菜单。
- `login_id` 中包含应用维度，格式为 `{userType}:{appId}:{userId}`。
- 授权码只能使用一次，过期或重复换取会被拒绝。

### 3.5 刷新 token

```http
POST /v3/api/auth/oauth2/refresh
Content-Type: application/x-www-form-urlencoded

grant_type=refresh_token&
client_id={client_id}&
refresh_token={refresh_token}
```

浏览器刷新 token 也不传 `client_secret`。后端会校验 refresh token 绑定的 `client_id`，防止跨应用刷新。

### 3.6 获取当前用户和菜单

```http
GET /v3/api/auth/oauth2/userinfo
Authorization: Bearer {access_token}
```

```http
GET /v3/api/center/current/user/menus
Authorization: Bearer {access_token}
```

菜单由后端按 token 中的 `app_id` 过滤：

- 返回当前应用菜单。
- 返回公共菜单。
- 不返回其他应用菜单。

## 四、外部 Web / SPA 应用

外部应用应使用标准授权码流程。浏览器端推荐 Authorization Code + PKCE。

### 4.1 发起授权

```http
GET /auth-center/oauth2/authorize?
  response_type=code&
  client_id={client_id}&
  redirect_uri={redirect_uri}&
  scope=all&
  state={random_state}&
  code_challenge={pkce_challenge}&
  code_challenge_method=S256
```

要求：

- `redirect_uri` 必须与应用登记值精确匹配。
- `state` 必须随机生成并在回调时校验。
- SPA / 浏览器应用生产接入必须使用 PKCE，不使用 `client_secret`。如果当前部署还未强制校验 PKCE，也建议调用方先按本节传递 `code_challenge/code_verifier`，便于后续无感启用。

### 4.2 回调换 token

```http
POST /v3/api/auth/oauth2/token
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code&
client_id={client_id}&
code={code}&
redirect_uri={redirect_uri}&
code_verifier={pkce_verifier}
```

服务端 Web 应用可以在自己的后端换 token，并在服务端安全保存 `client_secret`：

```http
POST /v3/api/auth/oauth2/token
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code&
client_id={client_id}&
client_secret={server_side_secret}&
code={code}&
redirect_uri={redirect_uri}
```

## 五、服务端应用和服务间调用

无用户上下文的后端服务调用使用 client credentials。

```http
POST /v3/api/auth/oauth2/token
Content-Type: application/x-www-form-urlencoded

grant_type=client_credentials&
client_id={client_id}&
client_secret={client_secret}&
scope=all
```

响应中的 access token 代表服务身份，不代表用户身份。调用下游服务时一般放入内部身份头：

```http
X-Internal-Authorization: Bearer {service_access_token}
```

如果请求本身有用户 token，必须保留用户 token：

```http
Authorization: Bearer {user_access_token}
X-Internal-Authorization: Bearer {service_access_token}
```

下游认证顺序是先识别用户 token，再识别服务 token。服务 token 不能冒充用户登录态。

## 六、前端集成示例

```ts
type AuthApp = {
  appId: number
  appName: string
  code: string
  clientId: string
}

async function loadApps(): Promise<AuthApp[]> {
  const res = await fetch('/auth-center/oauth2/apps', {
    headers: { Accept: 'application/json' },
  })
  const body = await res.json()
  if (!body.success) throw new Error(body.message || '应用列表加载失败')
  return body.result
}

async function login(clientId: string, username: string, password: string, vcode: string) {
  const form = new URLSearchParams({
    response_type: 'code',
    client_id: clientId,
    redirect_uri: `${window.location.origin}/login/callback`,
    state: crypto.randomUUID(),
    username,
    password,
    scope: 'all',
    loginType: 'PASSWORD',
    vcode,
  })

  const loginRes = await fetch('/auth-center/oauth2/doLogin', {
    method: 'POST',
    headers: { 'Content-Type': 'application/x-www-form-urlencoded' },
    body: form,
  })
  const loginBody = await loginRes.json()
  if (!loginBody.success) throw new Error(loginBody.message || '登录失败')
  const callbackUrl = new URL(loginBody.result, window.location.origin)
  if (callbackUrl.searchParams.get('state') !== form.get('state')) throw new Error('state 校验失败')

  const tokenForm = new URLSearchParams({
    grant_type: 'authorization_code',
    client_id: clientId,
    redirect_uri: form.get('redirect_uri')!,
    code: callbackUrl.searchParams.get('code')!,
  })
  const tokenRes = await fetch('/v3/api/auth/oauth2/token', {
    method: 'POST',
    headers: { 'Content-Type': 'application/x-www-form-urlencoded' },
    body: tokenForm,
  })
  const tokenBody = await tokenRes.json()
  if (!tokenBody.success) throw new Error(tokenBody.message || '换取 token 失败')
  return tokenBody.result
}
```

## 七、后端资源服务接入

下游资源服务只接受 token，不接收用户名密码。

### 7.1 Java 微服务

Java 业务服务接入 JBM 公共安全模块后，由 `SaOAuthFilterAuthStrategy` 处理：

- `Authorization: Bearer {user_access_token}`：绑定用户上下文，支持 `@SaCheckLogin`、权限注解。
- `X-Internal-Authorization: Bearer {service_access_token}`：无用户场景的服务互信。

业务代码通过当前用户上下文读取：

- `user_id`
- `username`
- `roles`
- `permissions`
- `appId`
- `clientId`

### 7.2 非 Java / Python 服务

非 Java 服务推荐按资源服务器方式接入：

1. 从 Auth 获取 JWKS 或公钥。
2. 校验 JWT 签名、`iss`、`aud`、`exp`。
3. 读取 claims：`user_id`、`client_id`、`app_id`、`roles`、`permissions`、`scope`。
4. 按接口要求校验角色、权限或 scope。

不要信任前端传入的 `user_id/app_id` 普通 header，必须以 token claims 为准。

## 八、安全要求

必须遵守：

- 浏览器端不出现 `client_secret`。
- 不把 `client_secret` 写入 localStorage、sessionStorage、cookie、URL、日志。
- `redirect_uri` 精确匹配，禁止任意域名回调。
- 授权码流程必须校验 `state`，浏览器应用生产接入必须使用 PKCE。
- access token 短有效期，refresh token 可撤销、可轮换。
- 后端菜单和接口权限必须按 token 重新判断。
- 服务端密钥只在应用创建/重置时一次性展示，落库存 hash 或加密值。

禁止做法：

- 浏览器登录请求固定携带 `client_secret`。
- 前端通过 `appId/userId` 参数自行选择菜单。
- 资源服务只根据前端传入的用户名、角色或菜单判断权限。
- 用服务 token 冒充用户访问需要用户态的接口。

## 九、常见问题

### 1. 用户登录成功但菜单不对

检查登录时使用的 `client_id` 是否属于目标应用。菜单接口按 token 中的 `app_id` 过滤，不按页面当前选择项过滤。

### 2. `client_credentials` 不带 secret 被拒绝

这是正确行为。client credentials 代表服务身份，必须使用 `client_secret` 或其他服务端认证方式。

### 3. 浏览器授权码登录不带 secret 是否安全

是正常模型。浏览器应用是 public client，不能用 secret 证明身份。安全性来自用户凭证、验证码、RSA 密码传输、一次性授权码、应用 `client_id`、token 签名、权限校验和后端菜单过滤。

### 4. 下游应用是否必须自己做登录页

第一方应用建议统一使用 JBM 登录页。外部应用可以跳转到认证中心授权页，不要在外部页面直接收集 JBM 用户密码。

### 5. 线上路径和文档示例不一致怎么办

本文示例使用当前统一入口部署路径：

- `/auth-center/**`：浏览器访问认证中心页面和公开应用列表。
- `/v3/api/auth/**`：经 Gateway 调用 Auth API。
- `/v3/api/center/**`：经 Gateway 调用 Center API。

如果下游直接接入 Gateway 或 Auth，请按实际网关路由调整前缀，核心协议字段不变。
